# Stamless CMS Headless — API v1

> Versión: v1 · Última actualización: 2026-09-18 · Ver también: [`docs/api/openapi.v1.yaml`](./openapi.v1.yaml)

## Introducción

La API v1 de Stamless CMS Headless expone, en modo **solo lectura** (salvo el envío de formularios), el contenido publicado de un tenant para que un frontend headless (Astro, Next.js, o cualquier cliente HTTP) lo consuma. Actualmente opera en un único idioma (`lang_iso = es`) y expone únicamente contenido publicado/activo — nunca borradores.

**Todo lo que devuelve o acepta esta API está scopeado por tenant** (el segmento `{tenant_slug}` del path) — cada tenant es una cuenta/cliente independiente de la plataforma, con su propio contenido, tokens, formularios y configuración. Ningún dato de un tenant es visible ni accesible con credenciales de otro (ver "Multi-tenant" más abajo). Las funciones más recientes de Console (SMTP propio, despliegue automático, límites de tokens) siguen el mismo principio: se configuran y aplican por tenant, nunca de forma global entre cuentas.

Toda la API requiere autenticación por **token Bearer** (Laravel Sanctum). No hay endpoints públicos sin token.

## Base URL

Stamless CMS Headless responde en varios dominios según el rol. El dominio de la API es **`APP_URL_API`** — no confundir con `APP_URL` (que es el de la landing) ni con `APP_URL_CONSOLE` (el panel admin).

```
{APP_URL_API}/v1/{tenant_slug}/...
```

Por ejemplo, para este tenant: `https://api.stamless.host/v1/cica360/pages`.

## Autenticación

Todas las rutas de `/v1/{tenant_slug}/*` exigen el header:

```
Authorization: Bearer {token}
```

El token es un **personal access token de Sanctum**, generado desde Console (ver más abajo). Cada token tiene un tenant dueño (el tenant del usuario que lo creó) y una o más **abilities**:

| Ability | Para qué sirve |
|---|---|
| `content:read` | Todos los endpoints `GET` (pages, posts, services, testimonials, menus, sliders, media) |
| `forms:submit` | `POST forms/{slug}/submit` |

Reglas de autorización, en orden:

1. **Sin header `Authorization`** → `401`.
2. **Token inválido, malformado o revocado** → `401`.
3. **Token válido pero sin la ability requerida por el endpoint** → `403`.
4. **Token válido pero de un tenant distinto al `{tenant_slug}` del path** → `403` (nunca se filtra si el tenant del path existe o no).
5. **`{tenant_slug}` no existe o está inactivo** → `404` (mismo mensaje genérico para ambos casos, para no revelar cuál de las dos razones aplica).

### Cómo crear un token (Console)

1. Iniciar sesión en Console (`studio.stamless.host`) con el usuario del tenant.
2. Ir a **Desarrolladores → API Tokens**.
3. **Crear token**: elegir un nombre descriptivo (ej. `frontend-produccion`), las abilities que necesita y una expiración (`Nunca`, `1 día`, `30/90 días`, `1 año`). Pasada esa fecha el token deja de funcionar solo (`401`), sin necesidad de revocarlo a mano.
4. El token en texto plano se muestra **una sola vez**, en un banner de advertencia. Hay que copiarlo antes de cerrar ese banner — Sanctum solo guarda el hash, así que si se pierde no hay forma de recuperarlo (hay que revocar y crear uno nuevo).
5. El listado siempre muestra el token enmascarado (`••••••••` + últimos 4 caracteres) y su expiración, nunca el valor completo.

### Cómo revocar un token

En **API Tokens**, botón **Revocar** en la fila del token. Es inmediato: cualquier request posterior con ese token responde `401`.

### Límites y alcance de los tokens

Todo lo de esta sección es **por tenant**: el tope de tokens, las abilities y el dominio permitido de un token se configuran y aplican exclusivamente para el tenant dueño de ese token — la actividad o configuración de un tenant nunca afecta el cupo o los tokens de otro.

Cada plan tiene un tope de tokens activos simultáneos, pensado para mantener ordenado el acceso a la API sin frenar un uso normal:

| Plan | Tokens activos permitidos |
|---|---|
| Free | 5 |
| Auspicio/Convenio | 10 |

Al llegar al límite, Console bloquea la creación de tokens nuevos hasta revocar alguno existente o esperar a que expire — no afecta a los tokens ya emitidos, que siguen funcionando con normalidad.

Al crear un token también se puede declarar su **plataforma** (`Web` o `App`) y, si es `Web`, un **dominio permitido** (`allowed_origin`):

- **`App`** (apps móviles, integraciones server-to-server): sin restricción de origen — un token de este tipo funciona desde cualquier cliente, ya que no existe un `Origin`/`Referer` de navegador significativo que exigir.
- **`Web`** con dominio configurado: la API exige que el request declare ese dominio exacto vía el header `Origin`, `Referer` o `X-Forwarded-Host` (en ese orden, según lo que el cliente envíe). Un token `Web` sin dominio configurado queda sin esta restricción — es responsabilidad de quien administra el tenant completarlo si quiere que tenga efecto real.

Esta validación es una capa adicional de defensa (útil sobre todo si un token quedara expuesto sin querer en un bundle de frontend), no un reemplazo de mantener el token fuera de código versionado.

## Envelope de response

Toda respuesta (éxito o error) sigue el mismo formato. Las claves con valor vacío/nulo **se omiten** (no se envían como `"key": null`), así que no todas las respuestas tienen exactamente las mismas claves.

```jsonc
{
  "success": true,       // boolean, siempre presente
  "message": "...",      // string, solo si hay un mensaje relevante
  "status_code": 200,    // int, siempre presente
  "data": { ... },       // el recurso o colección — solo en éxito
  "meta": { ... },       // paginación — solo en listados
  "links": { ... },      // links de paginación — solo en listados
  "errors": { ... }      // detalle de error — solo en 4xx/5xx con detalle estructurado
}
```

Listados paginados (`GET pages`, `GET posts`) agregan:

```jsonc
"meta": {
  "current_page": 1,
  "per_page": 15,
  "total": 42,
  "last_page": 3
},
"links": {
  "first": "https://.../pages?page=1",
  "prev": null,
  "next": "https://.../pages?page=2",
  "last": "https://.../pages?page=3"
}
```

`per_page` acepta `?per_page=N` en la query string (máximo 50, default 15).

## Errores

| Código | Cuándo | `errors.code` | Ejemplo |
|---|---|---|---|
| `401` | Sin header `Authorization` | `unauthenticated` | `{"success": false, "message": "No autenticado. Se requiere un token Bearer en el header Authorization.", "status_code": 401, "errors": {"code": "unauthenticated"}}` |
| `401` | Token inválido, malformado, expirado o revocado | `token_invalid` | `{"success": false, "message": "Token inválido o expirado.", "status_code": 401, "errors": {"code": "token_invalid"}}` |
| `403` | Token sin la ability requerida, o de otro tenant | `forbidden` | `{"success": false, "message": "No tiene permiso para acceder a este recurso.", "status_code": 403, "errors": {"code": "forbidden"}}` |
| `404` | Tenant/página/post/menú/slider/media no encontrado (o tenant inactivo) | `not_found` | `{"success": false, "message": "Página no encontrada.", "status_code": 404, "errors": {"code": "not_found"}}` |
| `422` | Validación (ej. `forms/submit` con campos requeridos faltantes) | `validation` | `{"success": false, "message": "Revisar los datos enviados.", "status_code": 422, "errors": {"code": "validation", "fields": {"message": ["El campo message es obligatorio."]}}}` |
| `429` | Rate limit superado | `too_many_requests` | `{"success": false, "message": "Demasiadas solicitudes. Intentar de nuevo más tarde.", "status_code": 429, "errors": {"code": "too_many_requests"}}` |

`errors.code` es estable y pensado para lógica de cliente (`switch` sobre el código) — el `message` es para mostrarlo tal cual a una persona, puede cambiar de texto sin previo aviso.

**Rate limiting**: 60 requests/minuto por IP en todos los endpoints de lectura; 10 requests/minuto por IP adicionales en `forms/{slug}/submit`.

## Multi-tenant

Cada request va scopeada por el segmento `{tenant_slug}` del path (ej. `cica360`), y se valida que el token pertenezca a ese mismo tenant. No existe forma de leer contenido de un tenant con el token de otro.

## Idioma (`lang_iso`)

Todos los endpoints devuelven contenido en `lang_iso = es` — no hay selector de idioma todavía. Si en el futuro se agrega soporte multi-idioma, será vía un segmento de path o un header dedicado.

- **Abilities**: `content:read`
- **Query params**: `type` (`page`|`landing`|`header`|`footer`|`legal`), `is_home` (`0`|`1`), `per_page` (1–50)

```json
  "status_code": 200,
  "data": [
    {

```

Detalle completo de un servicio publicado.

- **Abilities**: `content:read`
- **Response `404`** si no existe o no está publicado.

```json
{
  "success": true,
  "status_code": 200,
  "data": {
    "uuid": "0199b1a1-...",
    "slug": "servicio-de-ejemplo",
    "pretitle": null,
    "title": "Servicio de ejemplo",
    "subtitle": "Descripción breve de este servicio",
    "countries": [{ "iso": "UY", "name": "Uruguay" }],
    "content": {
      "intro": "Introducción de ejemplo sobre este servicio...",
      "offers": [{ "highlight": "Beneficio de ejemplo", "text": "..." }],
      "coverages": [{ "label": "Categoría de ejemplo", "intro": "...", "items": ["Ítem de ejemplo 1", "Ítem de ejemplo 2"] }],
      "why_choose_us": { "title": "¿Por qué elegirnos?", "text": "<p>Texto de ejemplo con <strong>formato enriquecido</strong>...</p>" },
      "tip": { "title": "Un consejo", "text": "Texto de ejemplo con información adicional." }
    },
    "meta": { "seo_title": "...", "seo_description": "..." },
    "links": [],
    "properties": {},
    "published_at": "2026-08-13T00:00:00.000000Z",
    "image": null,
    "image_detail": null,
    "footer": {
      "slug": "footer-principal",
      "blocks": [
        {
          "uuid": "0199b1a1-...",
          "type": "cta",
          "title": "Contacto",
          "content": {},
          "links": [],
          "properties": {},
          "sort_order": 1
        }
      ]
    }
  }
}
```

A diferencia de `posts`, `content` acá es un **objeto estructurado** (no HTML renderizado en bloque) — `intro`/`offers`/`coverages`/`why_choose_us`/`tip` son todos opcionales, puede llegar `{}` si el servicio no cargó ese contenido en Console. `why_choose_us` y `tip` son objetos `{ title, text }`, no strings.

**`footer` (2026-09-15, solo en `GET /services/{slug}`, NO en `GET /services`):** objeto `{ slug: string, blocks: Block[] }` con el Content tipo Footer seleccionado en Studio (`properties.footer_page_id`), o `null` si no tiene pie de página asignado. Sus bloques hijos se entregan completamente resueltos con la misma estructura que `content.footer_page` de los bloques de página.

**`image_detail` (2026-09-14, solo en `GET /services/{slug}`, NO en `GET /services`):** imagen secundaria y opcional — pensada para un header/banner más panorámico o apaisado en el detalle. `image` (presente en ambos endpoints) sigue siendo la imagen principal, usada como miniatura en el catálogo. Si `image_detail` es `null`, el consumidor debería usar `image` como fallback para el header del detalle — este fallback NO lo resuelve el API, queda del lado del cliente.

**Excepción (2026-09-14):** `why_choose_us.text` SÍ es HTML ya renderizado y sanitizado — es un `RichEditor` en Console (permite negrita/enlaces a mitad de frase), guardado internamente como documento TipTap/JSON y convertido a HTML antes de salir en la response (mismo mecanismo interno que usan algunos bloques de `pages` con campos `RichEditor`, ej. `rich_text`/`split`/`legal_notice` — pendiente de documentar el detalle de `pages.blocks.content` en esta guía). El resto de campos de texto de `services` (`intro`, `offers[].text`, `coverages[].items[]`, `tip.text`) siguen siendo texto plano — el consumidor no debería inyectar `why_choose_us.text` como texto (se verían las etiquetas), ni tratar el resto como HTML.

### `GET /menus/{slug}`

Menú con sus items activos, en **árbol recursivo** — cada item trae su propio `children[]` (mismo shape que el item padre), y cada uno de esos hijos puede a su vez traer más `children[]`, sin límite de profundidad del lado de la API (`MenuController::buildTree()` arma el árbol completo en memoria a partir de un único query eager-loaded, cero queries extra sin importar cuántos niveles tenga). En la práctica, Console (`MenuTreeBuilder`, ver ADR-045) limita la creación a **3 niveles** (menú → submenú → sub-submenú) — un frontend que consuma este endpoint puede recorrer `children` de forma genérica/recursiva sin necesidad de hardcodear "hasta 2 niveles de `<ul>` anidados"; si mañana se permite un 4º nivel desde Console, no hace falta ningún cambio de contrato acá.

- **Abilities**: `content:read`
- **Response `404`** si no existe.

**Ejemplo con submenú anidado** (agregado 2026-09-02 — antes el ejemplo solo mostraba items de nivel raíz con `children: []`, sin ilustrar cómo se ve un ítem con hijos reales):

```json
{
  "success": true,
  "status_code": 200,
  "data": {
    "uuid": "0199a3a1-...",
    "name": "Menú principal",
    "slug": "menu-principal",
    "items": [
      { "uuid": "0199a3a2-...", "title": "Home", "type": "page", "href": "/", "is_home": true, "target": "_self", "sort_order": 0, "children": [] },
      {
        "uuid": "0199a3a3-...",
        "title": "Servicios",
        "type": "page",
        "href": "/servicios",
        "is_home": false,
        "target": "_self",
        "sort_order": 2,
        "children": [
          {
            "uuid": "0199a3a5-...",
            "title": "Servicio de ejemplo",
            "type": "service",
            "href": "/servicios/servicio-de-ejemplo",
            "is_home": false,
            "target": "_self",
            "sort_order": 0,
            "children": [
              { "uuid": "0199a3a6-...", "title": "Enlace externo de ejemplo", "type": "external", "href": "https://ejemplo.com/pagina", "is_home": false, "target": "_blank", "sort_order": 0, "children": [] }
            ]
          },
          { "uuid": "0199a3a7-...", "title": "Otro servicio de ejemplo", "type": "service", "href": "/servicios/otro-servicio-de-ejemplo", "is_home": false, "target": "_self", "sort_order": 1, "children": [] }
        ]
      },
      { "uuid": "0199a3a4-...", "title": "Consultar ahora", "type": "page", "href": "/contacto", "is_home": false, "target": "_self", "sort_order": 4, "children": [] }
    ]
  }
}
```

Un `<li>` con submenú se identifica simplemente porque `children.length > 0` — no hay ningún campo `has_children`/`depth` separado; el propio array ya lo comunica. Un frontend típico renderiza esto con una función recursiva (`renderMenuItem(item)` que se llama a sí misma por cada `item.children`), en vez de un componente distinto por nivel.

`type` (agregado 2026-09-02): `page` | `post` | `service` | `external` | `custom`. `href` viene resuelto por el backend (`/` para la home, `/{slug}` para pages, `/blog/{slug}` para posts, `/servicios/{slug}` para services, o la URL cruda para items `external`/`custom`) — nunca hay que reconstruirlo en el frontend, ni siquiera para los items anidados.

### `GET /forms/{slug}`

Definición completa de un formulario activo: sus campos (dinámicos, definidos en Console) y los textos de la página de agradecimiento. Pensado para que el frontend arme el formulario sin hardcodear ningún campo — un tenant puede tener varios formularios (`contacto`, `cotizacion`, etc.), cada uno con su propio set de campos.

- **Abilities**: `content:read`
- **Response `404`** si no existe, está inactivo, o pertenece a otro tenant.

```json
{
  "success": true,
  "status_code": 200,
  "data": {
    "uuid": "0199d1a1-...",
    "slug": "contacto",
    "name": "Formulario de contacto",
    "description": null,
    "success_message": null,
    "redirect_url": null,
    "fields": [
      {
        "uuid": "0199d1a2-...",
        "name": "name",
        "label": "Nombre completo",
        "type": "text",
        "placeholder": "Ej. Juan Pérez",
        "help_text": null,
        "is_required": true,
        "validation_rules": ["required", "string", "max:255"],
        "options": null,
        "sort_order": 0
      },
      {
        "uuid": "0199d1a3-...",
        "name": "phone",
        "label": "Teléfono",
        "type": "tel_country",
        "placeholder": null,
        "help_text": null,
        "is_required": false,

        "options": null,
        "sort_order": 1

      {
        "uuid": "0199d1a4-...",

        "label": "Consulta",

      "alert_description": "Menos de 24 horas hábiles.",
      "button_label": "Enviar otra consulta"
```

`type` es uno de los valores de `FormFieldTypeEnum`: `text`, `email`, `tel`, `tel_country`, `textarea`, `select`, `checkbox`, `radio`, `number`, `date`, `file`, `hidden`. `tel_country` indica un teléfono con selector de país — la resolución de código de país e IP de origen queda del lado del frontend (ver `X-Origin-Country` más abajo). `options` solo trae valores en campos `select`/`radio`/`checkbox` (array de `{ value, label }`); en el resto es `null`. `thank_you.description` ya viene como HTML renderizado y sanitizado (es un `RichEditor` en Console), listo para insertar con `dangerouslySetInnerHTML`/`set:html` — no como texto plano. `{name}` en `thank_you.title` es un placeholder literal que el frontend puede reemplazar por el valor enviado en el campo `name` del submit, si existe.

### `POST /forms/{slug}/submit`

Envía un formulario público. Los campos aceptados dependen de los `fields` definidos para ese formulario (ver `GET /forms/{slug}`) — no hay un set fijo de campos a nivel de API. Nunca expone datos sensibles en la respuesta.

- **Abilities**: `forms:submit`
- **Rate limit**: 10/min por IP (además del límite general de 60/min)

**Request**:

```json
{
  "name": "Juan Pérez",
  "email": "juan@example.com",
  "phone": "099123456",
  "message": "Mensaje de ejemplo enviado desde el formulario."
}
```

**Headers opcionales** (metadatos de origen — ninguno es obligatorio, y ninguno participa de la validación de los campos del formulario):

| Header | Uso |
|---|---|
| `X-Forwarded-For` | IP real del visitante, cuando el frontend llama a la API desde un proxy server-side (ver "Cómo evitar exponer el token" más abajo) en vez de directamente desde el navegador. |
| `X-Origin-Country` | Código de país (ISO 3166-1 alpha-2, 2 letras) resuelto por el frontend a partir de la IP real, ANTES de reenviar el submit. Independiente de cualquier país que la persona elija a mano en el formulario. |

**Protección anti-bot (honeypot)**: si el request incluye un valor en alguno de los campos trampa `honeypot`, `_hp_check` o `_gotcha` (invisibles para una persona, pensados para que los complete un bot automatizado), la API responde `201` con éxito simulado — sin persistir el envío ni disparar notificaciones. El frontend no necesita distinguir este caso: simplemente no debe mostrar esos campos a la vista.

**Response `201`**:

```json
{
  "success": true,
  "message": "Formulario enviado correctamente.",
  "status_code": 201,
  "data": {
    "uuid": "0199a6d1-...",
    "thank_you": {
      "title": "¡Muchas gracias, Juan!",
      "description": "<p>Hemos recibido tu consulta correctamente...</p>",
      "alert_title": "Tiempo de respuesta estimado:",
      "alert_description": "Menos de 24 horas hábiles.",
      "button_label": "Enviar otra consulta"
    }
  }
}
```

`data.thank_you` viene resuelto en la misma respuesta del submit (mismo shape que `GET /forms/{slug}`, con `{name}` ya reemplazado por el valor enviado) — no hace falta un segundo request para mostrar la página de agradecimiento.

**Response `422`** (campo requerido faltante):

```json
{
  "success": false,
  "message": "Revisar los datos enviados.",
  "status_code": 422,
  "errors": { "code": "validation", "fields": { "message": ["El campo message es obligatorio."] } }
}
```

### `GET /settings/tracking`

IDs de tracking configurados en Console (Preferencias → Integraciones), para que el frontend los inyecte de forma diferida (lazy) sin necesidad de hardcodearlos por tenant.

- **Abilities**: `content:read`

```json
{
  "success": true,
  "status_code": 200,
  "data": {
    "meta_pixel_id": "1234567890123456",
    "gtm_id": "GTM-XXXXXXX"
  }
}
```

Cualquiera de las dos claves puede llegar en `null` si el tenant no lo configuró — el frontend debe omitir la carga del script correspondiente en ese caso, nunca asumir un valor por defecto.

## Buenas prácticas

- Guardar el token en una variable de entorno del build del frontend (ej. `PUBLIC_API_TOKEN` en Astro) y nunca commitearlo.
- Usar un token por frontend/entorno (`frontend-produccion`, `frontend-staging`) — así se puede revocar uno sin afectar al otro.
- Cachear agresivamente en el frontend: el contenido es publicado/estático, no cambia por request.
- Usar un `per_page` chico en listados cuando solo se necesitan los primeros N items — evita traer de más.
- Los links siempre traen `href` resuelto — no es necesario reconstruir rutas a mano a partir de `source_slug`, salvo que se necesite lógica de ruteo específica del frontend.
- Si el frontend corre en un entorno donde exponer el token en el navegador es un riesgo (ej. un sitio estático servido sin backend propio), lo recomendable es un pequeño proxy server-side (PHP, una función serverless, etc.) que guarde el token del lado del servidor y reenvíe únicamente los requests necesarios — ver "Cómo evitar exponer el token" más abajo.

### Cómo evitar exponer el token en el navegador

Un token con permiso `content:read` alcanza para leer todo el contenido publicado de un tenant. Si el frontend es un sitio 100% estático (sin servidor propio, ej. alojado en shared hosting), incluir el token directamente en el bundle de JavaScript lo deja visible para cualquiera que inspeccione el código fuente.

La solución recomendada es un proxy server-side liviano: un endpoint propio del hosting (PHP, una función serverless, un route handler) que guarda el token en una variable de entorno del servidor y arma el request a la API desde ahí, sin que el token viaje nunca al navegador. El frontend le pega a ese proxy, no directamente a `{APP_URL_API}`. Esto aplica sobre todo a `POST /forms/{slug}/submit` (que además necesita reenviar la IP real del visitante vía `X-Forwarded-For`, ver la tabla de headers opcionales más arriba) — para los endpoints de solo lectura (`GET`), un token con `allowed_origin` configurado (ver "Límites y alcance de los tokens") ya reduce el riesgo aunque quede embebido en el bundle.

## Ejemplos

### cURL

```bash
curl -s \
  -H "Authorization: Bearer TU_TOKEN" \
  -H "Accept: application/json" \
  "https://api.stamless.host/v1/cica360/pages/home"
```

```bash
curl -s -X POST \
  -H "Authorization: Bearer TU_TOKEN" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"name":"Juan Pérez","email":"juan@example.com","message":"Hola"}' \
  "https://api.stamless.host/v1/cica360/forms/contacto/submit"
```

### fetch (JS/TS)

```ts
const API_BASE = "https://api.stamless.host/v1/cica360";
const API_TOKEN = import.meta.env.PUBLIC_API_TOKEN;

async function getPage(slug: string) {
  const res = await fetch(`${API_BASE}/pages/${slug}`, {
    headers: {
      Authorization: `Bearer ${API_TOKEN}`,
      Accept: "application/json",
    },
  });

  const { success, data, message } = await res.json();

  if (!success) {
    throw new Error(message ?? `Error ${res.status}`);
  }

  return data;
}
```

## Funciones de Console relacionadas

Estas dos funciones no son endpoints de la API — se configuran en Console (**Preferencias**) y afectan cómo Stamless entrega los formularios de ese tenant. Se documentan acá porque son parte del flujo completo de "un formulario enviado por la API llega a destino".

### SMTP propio

**Configuración por tenant, opcional y aislada:** las credenciales SMTP viven en columnas propias de cada cuenta/tenant (nunca compartidas ni visibles entre tenants) y solo afectan los correos que envía ESE tenant. Por defecto, las notificaciones de un formulario (email al administrador + constancia opcional a quien completó el formulario) salen desde el remitente global de Stamless. En **Preferencias → SMTP propio**, un tenant puede cargar sus propias credenciales SMTP para que esos correos salgan desde su propio dominio:

| Campo | Uso |
|---|---|
| Servidor (host) | Dirección del servidor SMTP (ej. `smtp.gmail.com`, `mail.midominio.com`). |
| Puerto | Puerto del servidor (587 por defecto si se deja vacío). |
| Usuario | Usuario de autenticación SMTP. |
| Contraseña | Contraseña de autenticación. Se guarda cifrada; una vez guardada, el campo se muestra vacío y dejarlo así en una edición posterior **no la borra** — solo se reemplaza si se escribe una nueva. |
| Cifrado | `TLS`, `SSL` o ninguno, según lo que pida el proveedor SMTP. |
| Remitente (dirección y nombre) | El "From" que verá quien recibe el correo. Si se deja vacío, se usa el remitente global de Stamless como respaldo. |

El botón **Probar conexión** envía un correo de prueba con la configuración actual (sin necesidad de guardar primero) al usuario que está haciendo la prueba, para confirmar que las credenciales funcionan antes de darlas por buenas. Si no se configura ningún dato SMTP propio, todo sigue funcionando igual que antes: los correos salen por el remitente global de Stamless, sin ninguna acción adicional del tenant.

### Despliegue automático (Git)

**Configuración por tenant, opcional y aislada:** cada tenant vincula su PROPIO repositorio y su propio token de acceso — nunca hay un repo o token compartido entre cuentas. Para tenants cuyo frontend se publica desde un repositorio Git (un sitio estático desplegado por CI/CD, por ejemplo), Stamless puede disparar automáticamente un nuevo build/deploy cada vez que se publica un cambio de contenido relevante (página, post, servicio, menú, slider, configuración general), sin que nadie tenga que ir manualmente al repositorio a re-ejecutar el workflow.

En **Preferencias → Despliegue automático (Git)**:

| Campo | Uso |
|---|---|
| Repositorio | Nombre del repositorio de GitHub en formato `usuario/repositorio`. |
| Token de acceso | Personal Access Token de GitHub con permiso para disparar el workflow (`repository_dispatch`). Se guarda cifrado; igual que la contraseña SMTP, dejarlo vacío en una edición no borra el valor ya guardado. |
| Automatización activa | Interruptor que habilita o pausa los despliegues automáticos. Solo puede activarse si ya hay repositorio y token cargados — si falta alguno de los dos, queda forzado a apagado. |

Cuando está activo, cada cambio publicado dispara un evento hacia GitHub (`repository_dispatch`), que el workflow del repositorio del frontend recibe y usa para correr su propio proceso de build y despliegue — apuntando exclusivamente al repositorio configurado por ese tenant, nunca al de otro. Varios cambios seguidos en un lapso corto se agrupan en un único disparo por tenant (debounce) para no encadenar builds innecesarios; el debounce de un tenant nunca demora ni agrupa cambios de otro. Esta función es completamente independiente de la API pública v1: no depende de tokens ni abilities de `content:read`/`forms:submit`, es una integración server-to-server entre Stamless y GitHub.

## Limitaciones actuales

- No hay rotación automática de tokens ni notificación antes de que expiren — el frontend tiene que manejar un `401` por expiración igual que uno por revocación manual (mismo código, mismo mensaje "Token inválido o expirado.").
- El campo `Content-Type` de `Media.mime_type` viene tal cual se cargó el archivo — no hay validación/normalización adicional en la API.
- Los campos `image`/`avatar`/`media`/`background_image*` devuelven `null` hasta que se cargue el archivo correspondiente para ese contenido.
