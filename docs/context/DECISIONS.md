| Campo | Valor |

| **Fecha** | 2026-08-11 |

## ADR-013 — Esquema final de base de datos: contenido y negocio

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se implementa el esquema DBML "FINAL (MVP)" provisto por el humano para los módulos de **contenido y negocio**: `media`, `pages`, `blocks`, `posts`, `sliders`, `slides`, `menus`, `menu_items`, `plans`, `plan_features`, `subscriptions`, `payment_methods`, `invoices`, `invoice_items`, `transactions`, `modules`, `plan_module`, `tenant_modules`, `form_field_definitions`, `forms`, `form_fields`, `contacts`, `contact_activities`. Además se agregan `short_hash`, `is_active`, `plan` a `tenants` y `type` a `settings`. |
| **Contexto** | El mismo DBML incluye también una capa de auth avanzada (roles/permissions al estilo Spatie con `tenant_id`, Laravel Passport OAuth completo, Sanctum `personal_access_tokens`, `social_accounts`, y una migración de `users`↔`tenants` de columna `tenant_id` única a tabla pivote `tenant_user` con `role_id`). Implementar esa parte ahora reescribiría `HasTenant`, `User`, los paneles Filament y rompería los tests de aislamiento ya verdes, además de requerir instalar `laravel/passport` (con su propio generador de migraciones, no compatible 1:1 con el DBML de referencia si se escribe a mano). Se preguntó al humano y se acotó el alcance de esta sesión a contenido + negocio; auth avanzado queda pendiente con su propio ADR. |
| **Alternativas consideradas** | Implementar todo el DBML de una sola vez (descartada por riesgo de romper código ya testeado sin plan de migración de datos ni de los paneles Filament). |
| **Consecuencias** | 1) `tenants.short_hash` es `NOT NULL` con default calculado en Postgres (`substr(md5(random()::text),1,12)`) porque el proyecto no tiene `doctrine/dbal` instalado y no se puede usar `->change()` sobre una tabla con filas existentes; el modelo `Tenant` además lo asigna en `creating()` (mismo patrón que `HasUuid`) para que estar disponible en memoria. 2) `settings.tenant_id` se mantiene `NOT NULL` (el DBML lo sugiere nullable para settings de plataforma) porque cambiarlo requiere el mismo `doctrine/dbal` ausente y no hay caso de uso de settings globales aún; revisar con nuevo ADR si aparece. 3) `Contact.data` (jsonb) guarda las respuestas dinámicas del formulario; el cifrado selectivo de las claves marcadas `FormField.is_encrypted` dentro de ese jsonb es responsabilidad de la futura capa de servicio que procese el submit, no del modelo. 4) Todos los catálogos estáticos del DBML (`type`, `status`, `background_type`, etc.) se mapean a Enums PHP nativos (`App\Enums\*`) vía `casts()`, sin cambiar el tipo de columna (`varchar`) para no reñir con el DBML. 5) Tablas globales de plataforma sin `tenant_id`: `plans`, `plan_features`, `modules`, `plan_module`, `form_field_definitions` (coincide con ARCHITECTURE.md §3). 6) No se creó `HasSortOrder` ni trait de idioma: `sort_order` y `lang_iso` se manejan con default de columna + cast explícito por modelo, evitando lógica de negocio en traits genéricos. 7) No se implementan aún Filament Resources ni API — solo migraciones, modelos, enums y relaciones. |

## ADR-014 — Seeders idempotentes del MVP + Cliente 0 = CICA360

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se reemplaza el `DatabaseSeeder` monolítico por seeders separados por responsabilidad (`PlanSeeder`, `ModuleSeeder`, `FormFieldDefinitionSeeder`, `PlatformSeeder`, `Cliente0Seeder`), todos idempotentes vía `firstOrCreate`/`updateOrCreate`. Se confirma el nombre real de Cliente 0: **CICA360 (Centro Internacional de Consultoría y Asesoría)**, tenant `slug = cica360`. |
| **Contexto** | El scaffold inicial (2026-08-12) había sembrado un tenant placeholder `slug = cliente-0` con `User::create()`/`Tenant::create()` directos (no idempotentes: fallarían por violación de `unique` en un segundo `db:seed`). Ahora se conoce el nombre real del cliente y se necesita un seeder seguro de re-ejecutar en desarrollo. |
| **Consecuencias** | 1) `Cliente0Seeder` busca primero por el slug/email nuevos (`cica360` / `owner@cica360.com`) y, si no existen, hace fallback a los valores legado (`cliente-0` / `admin@cliente0.com`) para **renombrar in-place** el tenant y su usuario admin en vez de crear duplicados — importante porque el plan Free limita `max_users = 1` por tenant. En una base de datos nueva (sin el seed legado) simplemente crea los registros con los valores finales. 2) La contraseña de desarrollo (`password123`) solo se asigna al **crear** un usuario, nunca al renombrar uno existente, para no pisar credenciales ya rotadas en un entorno de desarrollo compartido. 3) La asignación formal de rol **OWNER** queda pendiente hasta el módulo de roles/permissions (ver ADR-013 / TASK.md #12); hoy el owner es, funcionalmente, el único usuario del tenant. 4) `Module.is_core = true` incluye `contacts` (el plan Free necesita recibir envíos de formulario sin depender de un módulo vertical de pago). 5) Orden de ejecución fijo en `DatabaseSeeder`: `PlanSeeder → ModuleSeeder → FormFieldDefinitionSeeder → PlatformSeeder → Cliente0Seeder` (el último depende de que el plan Free y los módulos core ya existan). |

## ADR-015 — Dominio y seguridad de Forms + Contacts

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se implementa `App\Services\ContactSubmissionService` como único punto de entrada para guardar un envío de `Form`: mapea `name`/`email`/`phone`/`company` a las columnas dedicadas de `Contact` (que ya cifran email/phone/company vía el cast `encrypted`) y cifra individualmente (`Crypt::encryptString`) cualquier otro campo marcado `FormField::is_encrypted` antes de guardarlo en `Contact::data` (jsonb); los campos no marcados quedan en texto plano dentro de ese mismo jsonb. Se agrega `ContactFormSubmitted` (Mailable Markdown, best-effort, nunca revierte el guardado del contacto si falla el envío), `App\Http\Resources\ContactResource` (whitelist explícito, nunca sensible), `App\Policies\ContactPolicy` (autorización tenant-aware por convención de Laravel, sin registro manual) y `App\Services\DataMasker` (helpers de enmascarado reutilizables para UI/logs). |
| **Contexto** | Bloque de trabajo explícitamente separado de los Filament Resources de contenido (Pages/Blocks/Sliders/Menus/Posts/Media), que implementa otro agente en paralelo. El objetivo era dejar lista la capa de dominio y seguridad de Forms + Contacts sin tocar ni duplicar ese trabajo. |
| **Alternativas consideradas** | (a) Guardar el payload dinámico como un array plano `[key => value]` sin metadata de cifrado embebida — descartada la idea de guardar un flag `is_encrypted` *dentro* del jsonb junto a cada valor; en su lugar, `FormField.is_encrypted` (por `name`) es la única fuente de verdad de qué claves están cifradas, tanto al guardar como al descifrar (`decryptData()`), evitando duplicar ese estado. (b) Emitir un Event + Listener para desacoplar el envío de mail — descartada por ahora a favor de una llamada directa y explícita dentro del service (más simple de leer/testear en este tamaño de MVP); se puede migrar a evento más adelante sin romper la firma pública de `submit()`. |
| **Consecuencias** | 1) Valores no escalares en un campo marcado `is_encrypted` (p. ej. un checkbox múltiple) se serializan a JSON antes de cifrar; `decryptData()` devuelve el string JSON tal cual, el llamador decide si hace `json_decode`. 2) `decryptData()` hace una query adicional (`form.fields`) por contacto; para listados masivos hay que eager-cargar `form.fields` antes de iterar (documentado en el docblock del método). 3) **Explícitamente fuera de alcance de este bloque** (dejado como TODO en `ContactPolicy::viewSensitive`): exigir re-autenticación (password/OTP) antes de exports o listados masivos de datos sensibles — no implementar sin ADR propio. 4) `Form.enable_honeypot`/`enable_recaptcha` siguen modelados en el esquema (ADR-013) pero **no** se aplican todavía dentro de `ContactSubmissionService::submit()` — el spam-filtering queda pendiente para no exceder el alcance pedido (solo cifrado + payload + notificación). 5) No se creó Filament Resource de Contacts en este bloque (lo cubre el otro agente cuando le llegue el turno); `ContactPolicy`/`ContactResource`/`DataMasker` quedan listos para que ese Resource los consuma sin reinventar la capa de seguridad. |

## ADR-016 — API REST pública v1 (Headless MVP)

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-16 |
| **Decisión** | Se implementa `GET /api/v1/{tenant_slug}/pages`, `pages/{slug}`, `posts`, `posts/{slug}`, `menus/{slug}`, `sliders/{slug}`, `media/{uuid}` y `POST /api/v1/{tenant_slug}/forms/{slug}/submit`, todos leyendo/escribiendo solo contenido publicado/activo, `lang_iso = 'es'` fijo (sin selector), con la envoltura JSON de ADR-009 (`success`, `message`, `data`, `meta`/`links` para paginación) aplicada de forma consistente vía traits reutilizables. La resolución de tenant se hace **explícitamente al inicio de cada acción de controller** (trait `ResolvesTenant::resolveTenant($tenant_slug)`, que reutiliza `TenantManager::setTenant()` — el mismo mecanismo que ya usan los paneles Filament), y no vía middleware. |
| **Contexto** | Se pidió el API REST mínima del MVP Headless para Cliente 0 (CICA360) reutilizando el sistema de tenancy existente ("no inventar otro sistema de tenancy"). Se investigó el pipeline de Laravel (`Kernel::sendRequestThroughRouter` → `Router::dispatchToRoute/findRoute/runRoute`) y se confirmó que el middleware **global** corre antes de que exista el route match, por lo que no puede leer `{tenant_slug}` de forma confiable; el middleware de grupo/ruta sí podría, pero su orden relativo al route-model-binding implícito es ambiguo y frágil para algo tan crítico como el aislamiento de tenant. Resolverlo explícitamente al inicio de cada acción es simple, explícito y fácil de testear. |
| **Alternativas consideradas** | (a) Middleware de ruta que lea `{tenant_slug}` — descartada por la ambigüedad de orden frente al binding implícito de otros parámetros de ruta. (b) Resolver el tenant por header/dominio como ya hace `ResolveTenant` para Filament — descartada como *única* vía porque el enunciado pide explícitamente el tenant en el path (`/v1/{tenant_slug}/...`) para consumo headless simple desde un frontend estático sin necesidad de configurar headers. |
| **Consecuencias** | 1) Cada controller de `App\Http\Controllers\Api\V1` extiende una `Controller` base que importa `ApiResponds` (envoltura ADR-009 + paginación) y `ResolvesTenant`. 2) Tenant inexistente **o** inactivo devuelven el mismo 404 genérico ("Tenant no encontrado") — no se distingue el motivo en el mensaje, para no filtrar existencia de tenants a terceros. 3) `pages/{slug}` eager-carga `blocks` filtrados por `is_visible = true` y ordenados por `sort_order`; `menus/{slug}` arma el árbol `parent_id` en memoria a partir de un único query (cero N+1 sin importar la profundidad) y resuelve `href` de items tipo Page/Post con dos queries `whereIn` batched (no una por item). Se agregó además un limiter dedicado `forms` (10/min por IP) solo para el endpoint de escritura. 8) Excepciones de rutas `api/*` (`ModelNotFoundException`, `NotFoundHttpException`, `ValidationException`, etc.) se interceptan en `bootstrap/app.php` (`withExceptions`) para devolver siempre la envoltura JSON de ADR-009, nunca la página HTML de error de Laravel. 9) **Fuera de alcance explícito de este bloque:** GraphQL, nuevos Filament Resources, frontend, billing — sin cambios. |

el mismo patrón se puede extender cuando haga falta (documentado también en `docs/api/v1.md`, sección "Pendientes conocidos"). 6) El Playground ejecuta requests HTTP reales contra `config('app.url')` desde el propio proceso de Laravel (server-side, vía `Http` facade) — no hay CORS ni proxy involucrado porque no corre en el navegador del admin. 7) Los tests de la API (`PageApiTest`, `ApiAuthTest`, `PostApiTest`) usan `Laravel\Sanctum\Sanctum::actingAs()` para simular tokens autenticados (excepto el test de revocación, que crea y revoca un token real para validar el flujo end-to-end) — **requieren que `laravel/sanctum` esté instalado** (`composer install`) para correr; no se pudieron ejecutar en este sandbox (sin PHP/Composer), solo verificación estática. |

## ADR-021 — Preferencias de usuario (idioma/zona horaria) + formateo de fechas amigable

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-17 |
| **Decisión** | (1) Se agregan `locale` (default `es`) y `timezone` (default `America/Lima`) a `users`, y una página nueva `App\Filament\Pages\Preferences` (grupo **Cuenta**) para que cada admin elija en qué idioma y zona horaria quiere ver Console — no afecta `lang_iso` del contenido del tenant, que sigue siendo siempre `es` en el MVP. (2) Se agrega `App\Support\FriendlyDate::format($date, ?User $user = null)`: si la fecha está a menos de 28 días de "ahora" devuelve un relativo natural localizado (`hace 5 min`, vía `Carbon::diffForHumans()`); si es más vieja, un absoluto abreviado con shape fijo `17 Ago 12:25 am` (día, mes corto propio — no el de Carbon —, hora 12h sin cero a la izquierda, meridiano en minúscula sin puntos, año solo si es distinto al actual) para que el resultado se vea igual en cualquier idioma salvo el nombre del mes. (3) Se aplica a las 3 columnas de fecha de `ApiTokens` (`last_used_at`, `expires_at`, `created_at`) como primer caso de uso real. (5) **2026-08-17, misma vuelta**: se agrega `App\Filament\Pages\ChangePassword` (`$shouldRegisterNavigation = false` — solo accesible desde el menú del avatar, no desde el sidebar) con campos `current_password` (`->currentPassword()`, valida contra el guard correcto), `password` (`Password::default()` + `->confirmed()`) y `password_confirmation`; guarda con `$user->update(['password' => ...])` apoyándose en el cast `'hashed'` de `User` (Laravel hashea solo al guardar). Se conecta `Panel::userMenuItems([...])` en `PanelCmsProvider` con dos `Filament\Navigation\MenuItem` ("Preferencias" → `Preferences::getUrl()`, "Cambiar contraseña" → `ChangePassword::getUrl()`), agregados al dropdown del avatar junto al toggle de tema y "Salir" que ya traía Filament por defecto. |
| **Contexto** | El humano pidió específicamente que las fechas de Console fueran "amigables y abreviadas" (no timestamps crudos ni ISO), respetando idioma y zona horaria configurables por el usuario (dio como referencia `America/Lima` y el formato `17 Ago 12:25 am`), con un recurso de settings para elegirlos. De paso reportó que la columna "Token" de `ApiTokens` se veía completamente vacía y que los tokens sin expiración no mostraban "Nunca" — ambos terminaron siendo bugs reales, no percepción. |
| **Alternativas consideradas** | (a) Guardar la preferencia de idioma/timezone a nivel **tenant** (reusando la tabla `settings` tenant-aware ya existente) — descartado: dos admins del mismo tenant podrían querer verlo distinto (ej. uno en Lima, otro en Montevideo); es una preferencia de visualización *del usuario*, no del negocio del tenant. (b) Usar el paquete `nesbot/carbon`'s `diffForHumans()` también para el caso "absoluto" (>= 28 días) — descartado: su meridiano (`a`/`A`) y abreviaturas de mes varían de forma no controlada entre locales de Carbon (CLDR), y se pidió un shape exacto (`17 Ago 12:25 am`); se hand-rolleó un mapa de meses abreviados propio (es/en/pt) para garantizar el mismo formato en los tres idiomas. |
| **Consecuencias** | 1) Los usuarios ya existentes en la base heredan los defaults de la migración (`es`/`America/Lima`) automáticamente vía `ADD COLUMN ... DEFAULT`, no hace falta backfill. 2) `FriendlyDate` es la única fuente de verdad para "fecha amigable" — cualquier tabla/columna nueva que necesite este formato debe usarla en vez de reinventar el formateo. 3) **Alcance de esta vuelta**: solo se aplicó a `ApiTokens`; extender el mismo patrón a las columnas `created_at`/`updated_at`/`published_at` de los demás Resources de Filament (Pages, Posts, Media, Contacts, etc.) queda pendiente como trabajo de seguimiento, no se tocó todo el Console de una — ver TASK.md. 4) No se pudo ejecutar `php artisan migrate`/tests en este sandbox (misma limitación de siempre); el humano tiene que correr `php artisan migrate` para la migración de `users` antes de que `Preferences` funcione. |

> **Actualización (2026-08-31):** el Tech Lead pidió explícitamente extender el rollout pendiente del punto (3) — "en todos los listados la fechas que sean amigables para humanos y si hay que mostrar fecha que muestre d:m:Y h:i a" — y ajustar el shape del caso absoluto. `FriendlyDate::absolute()` reemplaza el formato hand-rolleado por idioma (`17 Ago 12:25 am`, con mapa de meses abreviados es/en/pt) por el formato fijo pedido: `d:m:Y h:i a` (numérico, ej. `17:08:2026 12:25 am`) — más simple, sin depender del idioma del usuario, y elimina el mapa `MONTHS` que ya no hace falta. La parte relativa (`hace 5 min`, < 28 días) no cambia. Aplicado a las columnas `published_at` de `PageResource` y `PostResource` (antes usaban `->dateTime()` crudo, sin pasar por `FriendlyDate`) — con esto, TODAS las columnas de fecha visibles en algún listado de Console (`ApiTokens` + `PageResource` + `PostResource`, el resto de los Resources no muestra ninguna columna de fecha en su tabla) ya pasan por `FriendlyDate`, cerrando el pendiente del punto (3) de arriba.

| **Decisión** | Para rutas `/api/*`, el guest jamás se redirige a ningún lado: `$middleware->redirectGuestsTo(fn (Request $request) => $request->is('api/*') ? null : route('login'))` en `bootstrap/app.php`. El envelope de error 401 (ya existente en `$exceptions->render()`, ver ADR-018) ahora distingue "sin token" ("No autenticado. Enviá un token Bearer en el header Authorization.") de "token presente pero inválido/expirado/revocado" ("Token inválido o expirado.") según si el request trae un Bearer token, y agrega `errors.code: "unauthenticated"` en ambos casos. No se creó ninguna ruta `login` web ni se tocaron las abilities de Sanctum. |
| **Contexto** | Bug real reportado: un `GET /api/v1/{tenant}/pages` sin `Authorization` y sin header `Accept: application/json` (curl liso, clientes que no declaran Accept explícitamente) devolvía `422` con `{"message":"Route [login] not defined.",...}` en vez de `401`. Causa raíz (confirmada leyendo el vendor de Laravel, no supuesta): `Illuminate\Foundation\Configuration\ApplicationBuilder::withMiddleware()` registra por defecto `redirectGuestsTo(fn () => route('login'))` **antes** de correr el callback de `bootstrap/app.php` — como esta app es headless y nunca definió una ruta `login`, cuando `Authenticate::unauthenticated()` evalúa `$request->expectsJson() ? null : $this->redirectTo($request)` y `expectsJson()` da `false` (sin header `Accept: application/json`), intenta resolver `route('login')`, que no existe, y tira `Symfony\Component\Routing\Exception\RouteNotFoundException` (subclase de `\InvalidArgumentException`) **antes** de que la `AuthenticationException` real llegue a construirse — nuestro handler clasificaba esa `InvalidArgumentException` como `422` por diseño (para otros casos legítimos), de ahí el código y mensaje equivocados. Los tests existentes (`ApiAuthTest`) no lo detectaban porque todos usan `getJson()`, que fuerza `Accept: application/json` y evita el bug. |
| **Alternativas consideradas** | (a) Crear una ruta web `login` dummy solo para que `route('login')` no falle — descartada explícitamente por el Tech Lead: agrega una ruta sin propósito real a una app 100% headless, y no ataca la causa (el guest de `/api/*` nunca debería intentar redirigir a nada). (b) Capturar `RouteNotFoundException`/`InvalidArgumentException` con mensaje `"Route [login]..."` como caso especial en el handler y remapearlo a 401 — descartada: es un parche sobre el síntoma, más fráil que evitar que la excepción ocurra en primer lugar. |
| **Consecuencias** | 1) El mensaje 401 cambió de texto (antes: "No autenticado. Se requiere un token Bearer válido..."; ahora distingue sin-token vs token-inválido) — cualquier cliente que hiciera match exacto de string sobre el mensaje anterior debe actualizarse (no hay clientes reales todavía, así que no rompe nada en producción). 2) `docs/api/v1.md` documenta la tabla de errores con un mensaje de ejemplo para 401 — actualizar si se detecta desalineado. 3) El fix es específico a `/api/*`; el guest de rutas `web/*` (si alguna vez existieran, hoy solo `/`) sigue rompiendo contra `route('login')` porque no hay ruta de login web — fuera de alcance de este ADR, explícitamente no se creó (ver Decisión). |

## ADR-024 — Envelope de error API formalizado: taxonomía de `errors.code`, `errors.fields`, `ErrorEnvelope` compartido

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted (extiende ADR-023, refina ADR-009/ADR-018) |
| **Fecha** | 2026-08-19 |
| **Decisión** | (1) El handler global de excepciones de `bootstrap/app.php` (único punto que arma el envelope de error para toda `/api/*`, ver ADR-009/ADR-023) ahora mapea explícitamente cada tipo de excepción a un `errors.code` snake_case estable, pensado para que un frontend pueda hacer `switch` sobre el código sin parsear el `message` humano: `unauthenticated` (401, sin token), `token_invalid` (401, token presente pero inválido/expirado/revocado — antes compartía el mismo `errors.code` que "sin token"; ahora son distinguibles), `forbidden` (403), `not_found` (404), `validation` (422), `too_many_requests` (429), `server_error` (500). (2) `ValidationException` y la nueva `App\Exceptions\Api\MissingRequiredFieldsException` (ver más abajo) agregan `errors.fields: { campo: [mensajes] }` además de `errors.code`. (3) En `500`, `errors.detail` con el mensaje real de la excepción **solo aparece si `APP_DEBUG=true`** — nunca en producción, nunca un stack trace. (4) Se extrae `App\Support\Api\ErrorEnvelope` (clase estática, no trait — el handler de `bootstrap/app.php` es un `Closure` sin `$this`) como el único lugar que arma el JSON `{success:false, message, status_code, errors}`; `App\Http\Concerns\ApiResponds::error()` (usado por los controllers) ahora delega en `ErrorEnvelope::make()` en vez de duplicar el array — un error armado a mano en un controller y uno armado por una excepción no capturada tienen garantizado el mismo shape. (5) Nueva excepción de dominio `App\Exceptions\Api\MissingRequiredFieldsException` (extiende `InvalidArgumentException` a propósito, no `ValidationException`, porque los campos requeridos de un `Form` son datos configurables por tenant en runtime, no un rule set estático de Laravel) con un método `fields()` que arma el desglose por campo — usada por `ContactSubmissionService::assertRequiredFieldsPresent()`, consumida por `FormSubmissionController::store()`. Antes, un `POST forms/{slug}/submit` con campos faltantes devolvía un string libre en `errors.detail` (`"Faltan campos requeridos: email, message"`) sin desglose por campo. |
| **Contexto** | Ticket explícito del Tech Lead pidiendo formalizar el envelope de error con una tabla de mapeo completa (tipo de excepción → status → `errors.code` → mensaje), reutilización del helper existente (`ApiResponds`) en vez de duplicar lógica, y cobertura de test para los casos principales (sin token, token basura, token de otro tenant, validación de forms/submit, tenant inexistente). Esto es la continuación directa de ADR-023 (que ya había resuelto el bug de `route('login')` y sentado las bases de "sin token" vs "token inválido"), llevando esa distinción a una taxonomía completa y estable. |
| **Alternativas consideradas** | (a) Convertir `ContactSubmissionService::assertRequiredFieldsPresent()` para usar `Illuminate\Validation\Validator` real (construyendo un rule set `['campo' => 'required']` dinámico) y dejar que tire `ValidationException` de verdad — descartada: rompía `ContactSubmissionServiceTest::test_it_throws_when_a_required_field_is_missing()` (hace `expectException(InvalidArgumentException::class)`, y `ValidationException` no extiende esa clase), y además depende de que existan los archivos de idioma `resources/lang/es/validation.php` para que los mensajes salgan en español — no confirmado en este sandbox. Crear `MissingRequiredFieldsException extendiendo InvalidArgumentException` da el mismo `errors.fields` sin ninguno de esos dos riesgos. (b) Llamar a `App\Http\Concerns\ApiResponds::error()` directamente como `TraitName::metodo()` estático desde el handler de `bootstrap/app.php` — descartada: la semántica de PHP para llamar un método estático de un trait directamente (sin una clase que lo use) es ambigua/no garantizada, y no se pudo verificar empíricamente en este sandbox (sin PHP disponible) — se prefirió una clase estática dedicada (`ErrorEnvelope`), inequívoca. |
| **Consecuencias** | 1) Cualquier cliente que ya integró contra el `errors.code: "unauthenticated"` fijo de ADR-023 para TODOS los 401 va a ver que los 401 de token inválido ahora traen `token_invalid` en vez de `unauthenticated` — es un cambio de contrato menor, sin clientes reales todavía. 2) El `message` de 401/403/404/429/500 es **fijo por status, siempre** — nunca `$e->getMessage()` de la excepción real. Descubierto durante la implementación (confirmado por el humano corriendo `php artisan test`, ver PROGRESS.md): un primer intento que preservaba `$e->getMessage()` cuando existía (para no perder textos propios como `"El token no pertenece a este tenant."` de `ResolvesTenant`/ADR-018) filtraba el mensaje default de Sanctum sin traducir (`"Invalid ability provided."`) para abilities faltantes, porque `Illuminate\Foundation\Exceptions\Handler::prepareException()` (core de Laravel, corre ANTES que cualquier callback de `$exceptions->render()`) convierte incondicionalmente TODA `AuthorizationException` en `AccessDeniedHttpException` — perdiendo el tipo original — así que un `instanceof AuthorizationException` dentro del callback nunca matchea, y el fallback a `$e->getMessage()` terminaba exponiendo el texto interno de la librería. Mensaje fijo por status elimina esa clase entera de bug. El detalle específico de una excepción (cuando existe) solo se expone en `errors.detail`, y únicamente para `500` bajo `APP_DEBUG=true`. 3) `docs/api/v1.md` (tabla de errores) debe reflejar el nuevo `errors.code` por fila — actualizado en esta misma vuelta. 4) Test nuevo `tests/Feature/Api/V1/FormSubmissionApiTest.php` (no existía cobertura a nivel API para `forms/submit`, solo a nivel de servicio en `ContactSubmissionServiceTest`). |

## ADR-035 — `CountryEnum`: de 6 países fijos a ISO 3166-1 completo, campo opcional, reutilizable por cualquier tenant

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-31 |

| **Contexto** | Mismo día que ADR-034. La pregunta de fondo del Tech Lead — "de qué forma lo hacemos común o administrable por otros clientes" — tiene dos respuestas posibles según qué tipo de dato sea: (a) un catálogo CERRADO y UNIVERSAL como "países del mundo" no necesita ninguna gestión por tenant — el listado es el mismo para todos, así que un `Enum` PHP compartido (no una tabla `tenant_id`-scoped) YA satisface "reutilizable por cualquier tenant" sin configuración extra; (b) un catálogo ABIERTO y específico del negocio de cada tenant (ej. "rubro del cliente", "categoría interna") sí necesitaría algo tipo tags con autocompletado por tenant — pero esa es una necesidad genuinamente distinta a "país", y no hay un pedido concreto de ESE campo todavía (el mensaje del Tech Lead mezclaba ambas ideas, pero convergió en la lista ISO como pedido concreto). Por eso esta ADR resuelve países con el Enum ISO, y deja documentado como concepto aparte — no implementado — la idea de un sistema de tags genérico reutilizable, para cuando haya un pedido concreto que lo necesite (ver Alternativas). |
| **Alternativas consideradas** | (a) **Tabla `countries` con pivote**, administrable desde Filament — descartada: un catálogo de 249 países no cambia con el tiempo ni difiere entre tenants, mantenerlo en una tabla editable agrega una superficie de gestión (y de bugs: un tenant podría borrar o duplicar países) sin ningún beneficio real sobre un Enum estático. (b) **Config array (`config/countries.php`) + clase helper en vez de `enum` nativo** — considerada por el tamaño (249 casos es un archivo largo), descartada para mantener consistencia con la regla ya establecida del proyecto ("Usar Enums PHP para catálogos estáticos") y porque un `enum implements HasLabel` se integra con `Select::make(...)->options(CountryEnum::class)` de Filament sin código extra — el mismo patrón que ya usan `LanguageEnum`, `PublishStatusEnum`, etc. — mientras que una clase+config hubiera necesitado un adaptador. (c) **Campo `countries` como tags libres (freeform), con autocompletado cruzando valores usados en otros `services`** — la idea que el Tech Lead mencionó primero — descartada PARA PAÍS específicamente: un país tiene una respuesta objetivamente correcta y finita (no hay razón para que un tenant escriba "Perú", otro "PERU" y otro "peru" como 3 tags distintos), y freeform no da un código ISO limpio para mapear a bandera — perdería exactamente el requisito (b) del pedido ("ISO => NAME"). Esta idea de tags SÍ queda anotada como solución razonable para un campo *distinto* — una clasificación abierta y propia de cada tenant sin catálogo universal — si en el futuro se pide algo así (ej.: "categoría de servicio", "público objetivo"); implementarla requeriría una tabla polimórfica tipo `tags`/`taggables` con `tenant_id`, no un Enum. |
| **Consecuencias** | 1) `App\Enums\CountryEnum` reescrito — 6 casos → 249 (+ `Global`), valores en mayúscula (`ar` → `AR`, etc.), nuevos métodos `flagPath()`, `toApiArray()`, `resolveMany()`. 2) `App\Models\Service::countriesResolved()` nuevo. 3) `ServiceResource`: `countries` ya no `->required()`, `->searchable()` agregado al form y al filtro de tabla. 4) **`Cliente0ServicesSeeder` actualizado** — los 7 servicios ya sembrados usaban códigos en minúscula (`ar`, `uy`, ...) que ya NO existen en el Enum nuevo; el seeder se actualizó a mayúscula (`AR`, `UY`, `GLOBAL`, ...) — **el Tech Lead debe correr `php artisan db:seed --class=Cliente0ServicesSeeder` de nuevo** (usa `updateOrCreate`, es seguro re-ejecutarlo) para que los `services` ya sembrados queden con códigos válidos; si no se re-siembra, esas filas van a quedar con códigos viejos que `CountryEnum::tryFrom()` ya no reconoce (se descartan en silencio en `resolveMany()`, pero el filtro/badge de la tabla de Filament tampoco los va a poder resolver a un label). 5) Sin PHP en este sandbox — balance de llaves/paréntesis/corchetes verificado con un checker Python "PHP-aware" (ignora comentarios y strings) en los 4 archivos tocados, cuadra en los 4. 6) Sistema de tags genérico por tenant queda **explícitamente fuera de alcance** — anotado como alternativa futura, no como tarea pendiente, hasta que haya un pedido concreto de un campo con esa forma. |

## ADR-036 — Árbol de `pages` hasta 3 niveles (`parent_id`), solo organización en Studio

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-31 |
| **Decisión** | Se agrega `parent_id` autorreferenciado (nullable, `FK → pages.id`, `nullOnDelete()`) a la tabla `pages`, permitiendo un árbol de hasta **3 niveles** (página → subpágina → sub-subpágina), a pedido del Tech Lead: "como podemos hacer para armar arbol tree de navegacion hasta en 3 niveles, cuando una pagina tenga parent a otra pagina". Se confirmó explícitamente con el Tech Lead (`AskUserQuestion`) que el árbol es **"Solo organización"** — sirve para agrupar/anidar páginas dentro de Studio (listado con indentación visual `— `), pero **no cambia la URL pública de ninguna página**, que sigue siendo su `slug` plano tal cual hoy (`/mi-slug`, sin prefijos de la jerarquía). El límite de 3 niveles se hace cumplir a nivel de aplicación — el `Select::make('parent_id')` de `PageResource` filtra sus `options()` para excluir: la página misma (al editar), todos sus descendientes (evita ciclos, vía `descendantPageIds()`), y cualquier página que ya esté en profundidad 2 (elegirla como padre crearía un 4to nivel). `Page::depth()` calcula el nivel subiendo por `parent` (máximo 2 saltos + guard defensivo). La tabla de `PageResource` ahora hace eager-load de `parent.parent` y ordena páginas raíz primero, para que la indentación se pueda calcular sin N+1; se quitó `->sortable()` de la columna `title` para no romper ese orden agrupado con un clic de header. |
| **Contexto** | Mismo patrón ya probado en `menu_items.parent_id` (jerarquía de menús, 3 niveles, implementada el mismo día). El Tech Lead reusó la captura de pantalla de esa misma UI de menús como referencia visual al pedir esto para `pages`. La duda de diseño real era si "árbol" implicaba también anidar la URL pública (`/padre/hijo/nieto`) o si era puramente organizacional dentro del panel — se preguntó explícitamente porque tiene implicancias grandes: rutas anidadas exigirían tocar `ResolvesPublicLinks`, la API pública, y la unicidad de `slug` (hoy `[tenant_id, lang_iso, slug]`, plana). El Tech Lead confirmó la opción recomendada de mantenerlo simple: solo organización. |
| **Alternativas consideradas** | (a) **URL anidada según el árbol** (`/padre/hijo`) — la interpretación más "literal" de un árbol de navegación — descartada por decisión explícita del Tech Lead: hubiera requerido rediseñar `ResolvesPublicLinks`, la resolución de rutas del API pública, y cambiar la unicidad de `slug` de plana a compuesta con el path del ancestro, con mucho más riesgo y alcance para un MVP. (b) **Enforce de profundidad máxima con constraint de base de datos** (ej. columna `depth` calculada + `CHECK`) — descartada por simplicidad: un límite fijo y chico (3 niveles) alcanza con validarse en la capa de aplicación (Filament), evita lógica de triggers/constraints en Postgres para un valor que no va a crecer. (c) **Cascade delete de hijos al borrar el padre** — descartada a favor de `nullOnDelete()`: borrar una página no debería poder borrar en cascada otras páginas con contenido propio; los hijos quedan huérfanos (vuelven a nivel raíz) en vez de perderse. |
| **Consecuencias** | 1) Nueva migración `2026_08_31_000006_add_parent_id_to_pages_table.php` — el Tech Lead debe correr `php artisan migrate`. 2) `App\Models\Page`: `parent_id` agregado a `#[Fillable]`, nuevas relaciones `parent()`/`children()` y método `depth(): int`. 3) `PageResource`: nuevo campo `Select::make('parent_id')` en el tab "Configuración" (con `options()` filtrado por ciclos/profundidad), nuevo helper privado `descendantPageIds()`, `table()` con eager-load `parent.parent` + orden raíz-primero, columna `title` con indentación por profundidad y sin `->sortable()`. 4) Sin cambios en `ResolvesPublicLinks`, la API pública, ni la unicidad de `slug` — el contrato público de páginas es idéntico al de antes de esta ADR. 5) Balance de paréntesis/llaves/corchetes verificado (checker Python "PHP-aware") en los 3 archivos tocados — cuadra en los 3. 6) Gap conocido, no resuelto en esta ADR: el `Toggle::make('is_home')` dentro de `HeadingFieldset` (formulario) no impide todavía que dos páginas del mismo tenant queden marcadas como home a la vez — esa protección sí se agregó al toggle de la tabla de `PageResource` (columna `is_home`, ver PROGRESS.md), pero falta replicarla en el form. |

## ADR-037 — Fix de causa raíz: `saveRelationshipsUsing` corrompía campos `MediaUpload` al guardar

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-01 |
| **Decisión** | Se confirma y corrige la causa raíz del reporte crítico del Tech Lead ("si guardo sin cambiar nada, se borra/daña el jsonb"). El `$state` que recibe el closure `saveRelationshipsUsing()` del `Builder` de `blocks` (`PageResource.php`) — usado en vez del `->relationship()` nativo de Filament porque `Block` necesita creación/actualización/borrado manual ligado a `tenant_id`/`sort_order`/tipo — trae los campos `MediaUpload`/`FileUpload` de cada bloque en su **forma interna cruda**: un array de un solo elemento keyeado por el UUID que Livewire genera internamente para identificar el archivo (ej. `{"537a6e80-33e7-4085-8325-5b5a563fcd60": "4"}`), en vez del valor escalar limpio que Filament normalmente entrega (`"4"`). Esa limpieza la hace `Filament\Schemas\Components\StateCasts\FileUploadStateCast::get()` (`Arr::first($state)` en modo single), pero ese cast no se aplica sobre el estado que llega a un `saveRelationshipsUsing` manual — solo se aplica en el camino de deshidratación nativo de Filament (`->relationship()`), que este Builder no usa. El array crudo se guardaba tal cual en el jsonb de `content`/`links`/`properties`; el resolver público (`ResolvesPublicLinks::scalarOrNull()`, ADR de la sesión previa) descarta cualquier id no-escalar, así que la media se resuelve a `null` y desaparece del sitio público — mientras que en Studio el widget la sigue mostrando bien, porque para el propio `FileUpload` esa forma corrupta sigue siendo "un archivo cargado válido" (se reconstruye igual vía `hydrateFiles()`/`Arr::wrap()`). Esto explica por qué el bug pasó desapercibido durante toda la sesión: el contenido sembrado por seeders (`db:seed`) nunca pasa por este código, así que solo se manifestaba la primera vez que alguien guardaba una página real desde Studio — que coincidió con el trabajo reciente sobre el bloque de partners/logos, dando la falsa impresión de que "modificar ese bloque" fue la causa, cuando en realidad cualquier guardado de cualquier página con bloques que tengan `MediaUpload` (split, logos, features, services_grid, heading, hero manual, etc.) dispara el mismo bug — y como se resguardan TODOS los bloques de la página en el mismo guardado, un solo clic de "Guardar cambios" en Home corrompió a la vez la imagen del bloque `split` y los `media_id` de cada item del bloque `logos`. |
| **Diagnóstico** | Confirmado empíricamente, no solo por lectura de código: se agregó un `Log::info()` temporal en el `foreach` de `saveRelationshipsUsing` que registraba el valor real de `content.media_id` justo antes de guardar. El Tech Lead reprodujo el guardado sin cambios en Home y el log real (`storage/logs/laravel.log`) mostró `"media_id_value":{"537a6e80-...":"4"},"media_id_type":"array"` — la prueba directa del bug, no una hipótesis. El log de diagnóstico se retiró una vez confirmada la causa. |
| **Fix** | Nuevo helper `PageResource::unwrapFileUploadState(mixed $value): mixed` (`private static`, recursivo): detecta la firma exacta de esta forma cruda (array de 1 elemento, key con forma de UUID válido vía regex, valor escalar) y la colapsa al valor real; si no matchea esa firma exacta, recorre recursivamente cualquier sub-array sin tocarlo de otra forma. Se aplica a `content`, `properties` y `links` de cada bloque en `saveRelationshipsUsing`, antes de pasarlos a `$block->update()`/`create()`. La detección por regex de UUID (no simplemente "array de 1 elemento") es deliberada — evita falsos positivos sobre objetos legítimos de una sola propiedad (ej. `properties: {"background_color": "#fff"}`, que jamás tiene una key con forma de UUID). La recursión cubre los `MediaUpload` anidados dentro de items de `Repeater` (logos, features, services_grid), no solo los de nivel superior como `split`. |
| **Alternativas consideradas** | (a) **Usar `$component->getChildComponentContainer($key)->getState()` por item**, para forzar la deshidratación cast-aware de Filament en vez de normalizar a mano — descartada por no poder verificarse en este sandbox (sin PHP/Filament ejecutable) y por ser un cambio más invasivo sobre una API interna de Filament 5 (`Builder`/`Schema`) que no está completamente documentada; el fix elegido es autocontenido, no depende de comportamiento interno no verificado, y su corrección se probó con datos reales del log. (b) **Migrar `blocks` a `->relationship()` nativo** de Filament — resolvería esto de raíz de forma más "canónica", pero es un cambio de arquitectura grande (perder el control manual sobre `tenant_id`/`sort_order`/creación-actualización-borrado que motivó `saveRelationshipsUsing` en primer lugar) fuera de alcance de un fix puntual. (c) **Detección genérica sin regex de UUID** (cualquier array de 1 elemento con key string no-numérica) — descartada por riesgo real de falsos positivos sobre `properties`/`content` legítimos de una sola clave. |
| **Consecuencias** | 1) El guard de "estado vacío" agregado horas antes en la misma sesión (ver PROGRESS.md, mismo día) se mantiene como red de seguridad adicional — cubre un caso distinto (el Builder entero sin materializar) y sigue siendo válido. 2) Autoreparación: como el valor ya corrupto en la DB tiene la MISMA forma que este fix sabe normalizar, el próximo guardado de una página con bloques ya corrompidos los deja limpios sin intervención manual — aun así se recomienda correr `db:seed` para partir de datos conocidos-buenos y verificar. 3) No se tocó `ResolvesPublicLinks.php` — sus guards de la sesión previa (`scalarOrNull()`, `uniqueScalarIds()`) ya toleraban este dato corrupto sin tirar 500, solo lo ignoraban; este fix ataca la causa en el punto de guardado, no solo el síntoma en el punto de lectura. 4) **Verificado real por el Tech Lead** (no solo hipótesis): tras corregir también el bug de sliders (ver adenda de abajo), reprodujo el guardado sin cambios en Home y confirmó por log que `content.media_id` llega como escalar (`"4"`/`"5"`) — el fix funciona. |
| **Adenda 2026-09-01 — segundo bug de la misma familia, en `Forms\Components\Slider`** | Después de aplicar el fix de arriba, el Tech Lead reprodujo de nuevo y, con el inspector del navegador, confirmó que la imagen del `split` seguía sin verse — pero esta vez el `<img>` tenía el `src` correcto; lo que la ocultaba era el `style` inline: `filter: brightness(0%) saturate(0%) grayscale(0%) ... blur(0px); opacity: 0`. Causa: `Forms\Components\Slider` (usado por TODAS las propiedades de opacidad/brillo/saturación/contraste de `PropertiesSchema` y del bloque `heading`) tiene su propio state cast (`Filament\Schemas\Components\StateCasts\SliderStateCast::get()`, `floatval($state)`). Como el seeder nunca escribe estas propiedades explícitamente (solo pisa `pretitle`/`title`/`media_id`/`body`), su valor crudo en `$block->properties` es simplemente inexistente — `null` al leerlo — y `floatval(null)` da `0.0`, sin importar que el slider esté configurado con `->default(100)`: ese default de Filament solo se aplica al crear un registro desde cero, no al hidratar datos parciales vía `loadStateFromRelationshipsUsing`. Mismo patrón de fondo que el bug de `MediaUpload` (un state cast que no se aplica en el camino de carga/guardado manual de este Builder), pero en un componente distinto y con consecuencia distinta (imagen invisible por CSS, no imagen ausente). Fix: mapa exhaustivo `PageResource::SLIDER_PROPERTY_DEFAULTS` (cada `Slider::make('properties.X')` de la app con su default real — 100 para brillo/opacidad/saturación/contraste, 0 para escala de grises/sepia/rotación de matiz/desenfoque) + helper `backfillSliderDefaults()` que rellena cualquier key ausente sin pisar valores ya presentes (incluido un `0` puesto a propósito). Aplicado tanto en `loadStateFromRelationshipsUsing` (para que el propio widget en Studio ya muestre el valor correcto) como en `saveRelationshipsUsing` (red de seguridad adicional). Verificado con log real: `properties.media_opacity`/`media_brightness`/`media_filter_saturate`/`contrast`/`brightness` llegaron en `100` (no `0`) en el guardado de confirmación del Tech Lead — mensaje final: "quedó". |
