## ADR-003 — Multi-tenancy: single database + tenant_id

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-11 |
| **Decisión** | Un solo PostgreSQL. Aislamiento por columna `tenant_id` en tablas de negocio. Multi-domain por tenant. |
| **Contexto** | MVP multi-tenant para freelancers/agencias sin complejidad operativa de DB-por-tenant o schema-por-tenant. |

| **Consecuencias** | Obligatorio: global scopes, middleware de resolución, tests de aislamiento. No asumir aislamiento físico. Super-admin de plataforma separado de users de tenant. |

## ADR-013 — Esquema final de base de datos: contenido y negocio

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se implementa el esquema DBML "FINAL (MVP)" provisto por el humano para los módulos de **contenido y negocio**: `media`, `pages`, `blocks`, `posts`, `sliders`, `slides`, `menus`, `menu_items`, `plans`, `plan_features`, `subscriptions`, `payment_methods`, `invoices`, `invoice_items`, `transactions`, `modules`, `plan_module`, `tenant_modules`, `form_field_definitions`, `forms`, `form_fields`, `contacts`, `contact_activities`. Además se agregan `short_hash`, `is_active`, `plan` a `tenants` y `type` a `settings`. |
| **Contexto** | El mismo DBML incluye también una capa de auth avanzada (roles/permissions al estilo Spatie con `tenant_id`, Laravel Passport OAuth completo, Sanctum `personal_access_tokens`, `social_accounts`, y una migración de `users`↔`tenants` de columna `tenant_id` única a tabla pivote `tenant_user` con `role_id`). Implementar esa parte ahora reescribiría `HasTenant`, `User`, los paneles Filament y rompería los tests de aislamiento ya verdes, además de requerir instalar `laravel/passport` (con su propio generador de migraciones, no compatible 1:1 con el DBML de referencia si se escribe a mano). Se preguntó al humano y se acotó el alcance de esta sesión a contenido + negocio; auth avanzado queda pendiente con su propio ADR. |
| **Alternativas consideradas** | Implementar todo el DBML de una sola vez (descartada por riesgo de romper código ya testeado sin plan de migración de datos ni de los paneles Filament). |
| **Consecuencias** | 1) `tenants.short_hash` es `NOT NULL` con default calculado en Postgres (`substr(md5(random()::text),1,12)`) porque el proyecto no tiene `doctrine/dbal` instalado y no se puede usar `->change()` sobre una tabla con filas existentes; el modelo `Tenant` además lo asigna en `creating()` (mismo patrón que `HasUuid`) para que estar disponible en memoria. 2) `settings.tenant_id` se mantiene `NOT NULL` (el DBML lo sugiere nullable para settings de plataforma) porque cambiarlo requiere el mismo `doctrine/dbal` ausente y no hay caso de uso de settings globales aún; revisar con nuevo ADR si aparece. 3) `Contact.data` (jsonb) guarda las respuestas dinámicas del formulario; el cifrado selectivo de las claves marcadas `FormField.is_encrypted` dentro de ese jsonb es responsabilidad de la futura capa de servicio que procese el submit, no del modelo. 4) Todos los catálogos estáticos del DBML (`type`, `status`, `background_type`, etc.) se mapean a Enums PHP nativos (`App\Enums\*`) vía `casts()`, sin cambiar el tipo de columna (`varchar`) para no reñir con el DBML. 5) Tablas globales de plataforma sin `tenant_id`: `plans`, `plan_features`, `modules`, `plan_module`, `form_field_definitions` (coincide con ARCHITECTURE.md §3). 6) No se creó `HasSortOrder` ni trait de idioma: `sort_order` y `lang_iso` se manejan con default de columna + cast explícito por modelo, evitando lógica de negocio en traits genéricos. 7) No se implementan aún Filament Resources ni API — solo migraciones, modelos, enums y relaciones. |

## ADR-014 — Seeders idempotentes del MVP + Cliente 0 = CICA360

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se reemplaza el `DatabaseSeeder` monolítico por seeders separados por responsabilidad (`PlanSeeder`, `ModuleSeeder`, `FormFieldDefinitionSeeder`, `PlatformSeeder`, `Cliente0Seeder`), todos idempotentes vía `firstOrCreate`/`updateOrCreate`. Se confirma el nombre real de Cliente 0: **CICA360 (Centro Internacional de Consultoría y Asesoría)**, tenant `slug = cica360`. |
| **Contexto** | El scaffold inicial (2026-08-12) había sembrado un tenant placeholder `slug = cliente-0` con `User::create()`/`Tenant::create()` directos (no idempotentes: fallarían por violación de `unique` en un segundo `db:seed`). Ahora se conoce el nombre real del cliente y se necesita un seeder seguro de re-ejecutar en desarrollo. |
| **Consecuencias** | 1) `Cliente0Seeder` busca primero por el slug/email nuevos (`cica360` / `owner@cica360.com`) y, si no existen, hace fallback a los valores legado (`cliente-0` / `admin@cliente0.com`) para **renombrar in-place** el tenant y su usuario admin en vez de crear duplicados — importante porque el plan Free limita `max_users = 1` por tenant. En una base de datos nueva (sin el seed legado) simplemente crea los registros con los valores finales. 2) La contraseña de desarrollo (`password123`) solo se asigna al **crear** un usuario, nunca al renombrar uno existente, para no pisar credenciales ya rotadas en un entorno de desarrollo compartido. 3) La asignación formal de rol **OWNER** queda pendiente hasta el módulo de roles/permissions (ver ADR-013 / TASK.md #12); hoy el owner es, funcionalmente, el único usuario del tenant. 4) `Module.is_core = true` incluye `contacts` (el plan Free necesita recibir envíos de formulario sin depender de un módulo vertical de pago). 5) Orden de ejecución fijo en `DatabaseSeeder`: `PlanSeeder → ModuleSeeder → FormFieldDefinitionSeeder → PlatformSeeder → Cliente0Seeder` (el último depende de que el plan Free y los módulos core ya existan). |

## ADR-015 — Dominio y seguridad de Forms + Contacts

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-13 |
| **Decisión** | Se implementa `App\Services\ContactSubmissionService` como único punto de entrada para guardar un envío de `Form`: mapea `name`/`email`/`phone`/`company` a las columnas dedicadas de `Contact` (que ya cifran email/phone/company vía el cast `encrypted`) y cifra individualmente (`Crypt::encryptString`) cualquier otro campo marcado `FormField::is_encrypted` antes de guardarlo en `Contact::data` (jsonb); los campos no marcados quedan en texto plano dentro de ese mismo jsonb. Se agrega `ContactFormSubmitted` (Mailable Markdown, best-effort, nunca revierte el guardado del contacto si falla el envío), `App\Http\Resources\ContactResource` (whitelist explícito, nunca sensible), `App\Policies\ContactPolicy` (autorización tenant-aware por convención de Laravel, sin registro manual) y `App\Services\DataMasker` (helpers de enmascarado reutilizables para UI/logs). |
| **Contexto** | Bloque de trabajo explícitamente separado de los Filament Resources de contenido (Pages/Blocks/Sliders/Menus/Posts/Media), que implementa otro agente en paralelo. El objetivo era dejar lista la capa de dominio y seguridad de Forms + Contacts sin tocar ni duplicar ese trabajo. |
| **Alternativas consideradas** | (a) Guardar el payload dinámico como un array plano `[key => value]` sin metadata de cifrado embebida — descartada la idea de guardar un flag `is_encrypted` *dentro* del jsonb junto a cada valor; en su lugar, `FormField.is_encrypted` (por `name`) es la única fuente de verdad de qué claves están cifradas, tanto al guardar como al descifrar (`decryptData()`), evitando duplicar ese estado. (b) Emitir un Event + Listener para desacoplar el envío de mail — descartada por ahora a favor de una llamada directa y explícita dentro del service (más simple de leer/testear en este tamaño de MVP); se puede migrar a evento más adelante sin romper la firma pública de `submit()`. |
| **Consecuencias** | 1) Valores no escalares en un campo marcado `is_encrypted` (p. ej. un checkbox múltiple) se serializan a JSON antes de cifrar; `decryptData()` devuelve el string JSON tal cual, el llamador decide si hace `json_decode`. 2) `decryptData()` hace una query adicional (`form.fields`) por contacto; para listados masivos hay que eager-cargar `form.fields` antes de iterar (documentado en el docblock del método). 3) **Explícitamente fuera de alcance de este bloque** (dejado como TODO en `ContactPolicy::viewSensitive`): exigir re-autenticación (password/OTP) antes de exports o listados masivos de datos sensibles — no implementar sin ADR propio. 4) `Form.enable_honeypot`/`enable_recaptcha` siguen modelados en el esquema (ADR-013) pero **no** se aplican todavía dentro de `ContactSubmissionService::submit()` — el spam-filtering queda pendiente para no exceder el alcance pedido (solo cifrado + payload + notificación). 5) No se creó Filament Resource de Contacts en este bloque (lo cubre el otro agente cuando le llegue el turno); `ContactPolicy`/`ContactResource`/`DataMasker` quedan listos para que ese Resource los consuma sin reinventar la capa de seguridad. |

## ADR-023 — Fix: 401 de la API no debe depender de `route('login')`

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted (extendido por ADR-024) |
| **Fecha** | 2026-08-19 |
| **Decisión** | Para rutas `/api/*`, el guest jamás se redirige a ningún lado: `$middleware->redirectGuestsTo(fn (Request $request) => $request->is('api/*') ? null : route('login'))` en `bootstrap/app.php`. El envelope de error 401 (ya existente en `$exceptions->render()`, ver ADR-018) ahora distingue "sin token" ("No autenticado. Enviá un token Bearer en el header Authorization.") de "token presente pero inválido/expirado/revocado" ("Token inválido o expirado.") según si el request trae un Bearer token, y agrega `errors.code: "unauthenticated"` en ambos casos. No se creó ninguna ruta `login` web ni se tocaron las abilities de Sanctum. |
| **Contexto** | Bug real reportado: un `GET /api/v1/{tenant}/pages` sin `Authorization` y sin header `Accept: application/json` (curl liso, clientes que no declaran Accept explícitamente) devolvía `422` con `{"message":"Route [login] not defined.",...}` en vez de `401`. Causa raíz (confirmada leyendo el vendor de Laravel, no supuesta): `Illuminate\Foundation\Configuration\ApplicationBuilder::withMiddleware()` registra por defecto `redirectGuestsTo(fn () => route('login'))` **antes** de correr el callback de `bootstrap/app.php` — como esta app es headless y nunca definió una ruta `login`, cuando `Authenticate::unauthenticated()` evalúa `$request->expectsJson() ? null : $this->redirectTo($request)` y `expectsJson()` da `false` (sin header `Accept: application/json`), intenta resolver `route('login')`, que no existe, y tira `Symfony\Component\Routing\Exception\RouteNotFoundException` (subclase de `\InvalidArgumentException`) **antes** de que la `AuthenticationException` real llegue a construirse — nuestro handler clasificaba esa `InvalidArgumentException` como `422` por diseño (para otros casos legítimos), de ahí el código y mensaje equivocados. Los tests existentes (`ApiAuthTest`) no lo detectaban porque todos usan `getJson()`, que fuerza `Accept: application/json` y evita el bug. |
| **Alternativas consideradas** | (a) Crear una ruta web `login` dummy solo para que `route('login')` no falle — descartada explícitamente por el Tech Lead: agrega una ruta sin propósito real a una app 100% headless, y no ataca la causa (el guest de `/api/*` nunca debería intentar redirigir a nada). (b) Capturar `RouteNotFoundException`/`InvalidArgumentException` con mensaje `"Route [login]..."` como caso especial en el handler y remapearlo a 401 — descartada: es un parche sobre el síntoma, más fráil que evitar que la excepción ocurra en primer lugar. |
| **Consecuencias** | 1) El mensaje 401 cambió de texto (antes: "No autenticado. Se requiere un token Bearer válido..."; ahora distingue sin-token vs token-inválido) — cualquier cliente que hiciera match exacto de string sobre el mensaje anterior debe actualizarse (no hay clientes reales todavía, así que no rompe nada en producción). 2) `docs/api/v1.md` documenta la tabla de errores con un mensaje de ejemplo para 401 — actualizar si se detecta desalineado. 3) El fix es específico a `/api/*`; el guest de rutas `web/*` (si alguna vez existieran, hoy solo `/`) sigue rompiendo contra `route('login')` porque no hay ruta de login web — fuera de alcance de este ADR, explícitamente no se creó (ver Decisión). |

## ADR-024 — Envelope de error API formalizado: taxonomía de `errors.code`, `errors.fields`, `ErrorEnvelope` compartido

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted (extiende ADR-023, refina ADR-009/ADR-018) |
| **Fecha** | 2026-08-19 |
| **Decisión** | (1) El handler global de excepciones de `bootstrap/app.php` (único punto que arma el envelope de error para toda `/api/*`, ver ADR-009/ADR-023) ahora mapea explícitamente cada tipo de excepción a un `errors.code` snake_case estable, pensado para que un frontend pueda hacer `switch` sobre el código sin parsear el `message` humano: `unauthenticated` (401, sin token), `token_invalid` (401, token presente pero inválido/expirado/revocado — antes compartía el mismo `errors.code` que "sin token"; ahora son distinguibles), `forbidden` (403), `not_found` (404), `validation` (422), `too_many_requests` (429), `server_error` (500). (2) `ValidationException` y la nueva `App\Exceptions\Api\MissingRequiredFieldsException` (ver más abajo) agregan `errors.fields: { campo: [mensajes] }` además de `errors.code`. (3) En `500`, `errors.detail` con el mensaje real de la excepción **solo aparece si `APP_DEBUG=true`** — nunca en producción, nunca un stack trace. (4) Se extrae `App\Support\Api\ErrorEnvelope` (clase estática, no trait — el handler de `bootstrap/app.php` es un `Closure` sin `$this`) como el único lugar que arma el JSON `{success:false, message, status_code, errors}`; `App\Http\Concerns\ApiResponds::error()` (usado por los controllers) ahora delega en `ErrorEnvelope::make()` en vez de duplicar el array — un error armado a mano en un controller y uno armado por una excepción no capturada tienen garantizado el mismo shape. (5) Nueva excepción de dominio `App\Exceptions\Api\MissingRequiredFieldsException` (extiende `InvalidArgumentException` a propósito, no `ValidationException`, porque los campos requeridos de un `Form` son datos configurables por tenant en runtime, no un rule set estático de Laravel) con un método `fields()` que arma el desglose por campo — usada por `ContactSubmissionService::assertRequiredFieldsPresent()`, consumida por `FormSubmissionController::store()`. Antes, un `POST forms/{slug}/submit` con campos faltantes devolvía un string libre en `errors.detail` (`"Faltan campos requeridos: email, message"`) sin desglose por campo. |
| **Contexto** | Ticket explícito del Tech Lead pidiendo formalizar el envelope de error con una tabla de mapeo completa (tipo de excepción → status → `errors.code` → mensaje), reutilización del helper existente (`ApiResponds`) en vez de duplicar lógica, y cobertura de test para los casos principales (sin token, token basura, token de otro tenant, validación de forms/submit, tenant inexistente). Esto es la continuación directa de ADR-023 (que ya había resuelto el bug de `route('login')` y sentado las bases de "sin token" vs "token inválido"), llevando esa distinción a una taxonomía completa y estable. |
| **Alternativas consideradas** | (a) Convertir `ContactSubmissionService::assertRequiredFieldsPresent()` para usar `Illuminate\Validation\Validator` real (construyendo un rule set `['campo' => 'required']` dinámico) y dejar que tire `ValidationException` de verdad — descartada: rompía `ContactSubmissionServiceTest::test_it_throws_when_a_required_field_is_missing()` (hace `expectException(InvalidArgumentException::class)`, y `ValidationException` no extiende esa clase), y además depende de que existan los archivos de idioma `resources/lang/es/validation.php` para que los mensajes salgan en español — no confirmado en este sandbox. Crear `MissingRequiredFieldsException extendiendo InvalidArgumentException` da el mismo `errors.fields` sin ninguno de esos dos riesgos. (b) Llamar a `App\Http\Concerns\ApiResponds::error()` directamente como `TraitName::metodo()` estático desde el handler de `bootstrap/app.php` — descartada: la semántica de PHP para llamar un método estático de un trait directamente (sin una clase que lo use) es ambigua/no garantizada, y no se pudo verificar empíricamente en este sandbox (sin PHP disponible) — se prefirió una clase estática dedicada (`ErrorEnvelope`), inequívoca. |
| **Consecuencias** | 1) Cualquier cliente que ya integró contra el `errors.code: "unauthenticated"` fijo de ADR-023 para TODOS los 401 va a ver que los 401 de token inválido ahora traen `token_invalid` en vez de `unauthenticated` — es un cambio de contrato menor, sin clientes reales todavía. 2) El `message` de 401/403/404/429/500 es **fijo por status, siempre** — nunca `$e->getMessage()` de la excepción real. Descubierto durante la implementación (confirmado por el humano corriendo `php artisan test`, ver PROGRESS.md): un primer intento que preservaba `$e->getMessage()` cuando existía (para no perder textos propios como `"El token no pertenece a este tenant."` de `ResolvesTenant`/ADR-018) filtraba el mensaje default de Sanctum sin traducir (`"Invalid ability provided."`) para abilities faltantes, porque `Illuminate\Foundation\Exceptions\Handler::prepareException()` (core de Laravel, corre ANTES que cualquier callback de `$exceptions->render()`) convierte incondicionalmente TODA `AuthorizationException` en `AccessDeniedHttpException` — perdiendo el tipo original — así que un `instanceof AuthorizationException` dentro del callback nunca matchea, y el fallback a `$e->getMessage()` terminaba exponiendo el texto interno de la librería. Mensaje fijo por status elimina esa clase entera de bug. El detalle específico de una excepción (cuando existe) solo se expone en `errors.detail`, y únicamente para `500` bajo `APP_DEBUG=true`. 3) `docs/api/v1.md` (tabla de errores) debe reflejar el nuevo `errors.code` por fila — actualizado en esta misma vuelta. 4) Test nuevo `tests/Feature/Api/V1/FormSubmissionApiTest.php` (no existía cobertura a nivel API para `forms/submit`, solo a nivel de servicio en `ContactSubmissionServiceTest`). |

| **Decisión** | El Tech Lead pidió repensar el campo `countries` de `Service` (ADR-034) con 3 objetivos: (1) que NO sea requerido — "muy pocos son internacionales" — la mayoría de los servicios de un tenant no necesitan país; (2) que cubra "todos los países del mundo con su ISO => NAME" en vez de los 6 específicos de CICA360, para poder elegir cualquier país; (3) que el diseño sea "reutilizado por cualquier tenant", no algo que haya que rehacer por cliente. También propuso, como alternativa, un campo custom genérico de tipo tags con autocompletado en base a valores ya usados en otros servicios. Implementado — se descartó la vía de tags libres para este campo específico y se resolvió con el catálogo ISO: `App\Enums\CountryEnum` pasa de 6 casos a **249 casos** (el listado ISO 3166-1 alpha-2 completo, nombres en español vía CLDR), más un caso `Global` (no-ISO) para servicios sin país puntual. El VALOR de cada caso es el código ISO en MAYÚSCULA (`PE`, `AR`, `US`, ...) — es la misma clave que usará la convención de banderas del frontend (`media/flags/flag_{ISO}.webp`, ver `flagPath()`). Se agregaron 3 helpers pensados para cuando se construya la API pública de `services` (fuera de alcance todavía, ver ADR-034): `toApiArray()` (`['iso' => ..., 'name' => ...]` por caso), `resolveMany(array $codes)` (mapea un array de códigos guardados a su forma resuelta, descartando en silencio códigos inválidos/viejos) y `flagPath()`. `Service::countriesResolved()` expone esto mismo a nivel de modelo. En `ServiceResource`: `->required()` eliminado del `Select`, `->searchable()` agregado tanto ahí como en el `SelectFilter` de la tabla (imprescindible con 249 opciones). |
| **Contexto** | Mismo día que ADR-034. La pregunta de fondo del Tech Lead — "de qué forma lo hacemos común o administrable por otros clientes" — tiene dos respuestas posibles según qué tipo de dato sea: (a) un catálogo CERRADO y UNIVERSAL como "países del mundo" no necesita ninguna gestión por tenant — el listado es el mismo para todos, así que un `Enum` PHP compartido (no una tabla `tenant_id`-scoped) YA satisface "reutilizable por cualquier tenant" sin configuración extra; (b) un catálogo ABIERTO y específico del negocio de cada tenant (ej. "rubro del cliente", "categoría interna") sí necesitaría algo tipo tags con autocompletado por tenant — pero esa es una necesidad genuinamente distinta a "país", y no hay un pedido concreto de ESE campo todavía (el mensaje del Tech Lead mezclaba ambas ideas, pero convergió en la lista ISO como pedido concreto). Por eso esta ADR resuelve países con el Enum ISO, y deja documentado como concepto aparte — no implementado — la idea de un sistema de tags genérico reutilizable, para cuando haya un pedido concreto que lo necesite (ver Alternativas). |
| **Alternativas consideradas** | (a) **Tabla `countries` con pivote**, administrable desde Filament — descartada: un catálogo de 249 países no cambia con el tiempo ni difiere entre tenants, mantenerlo en una tabla editable agrega una superficie de gestión (y de bugs: un tenant podría borrar o duplicar países) sin ningún beneficio real sobre un Enum estático. (b) **Config array (`config/countries.php`) + clase helper en vez de `enum` nativo** — considerada por el tamaño (249 casos es un archivo largo), descartada para mantener consistencia con la regla ya establecida del proyecto ("Usar Enums PHP para catálogos estáticos") y porque un `enum implements HasLabel` se integra con `Select::make(...)->options(CountryEnum::class)` de Filament sin código extra — el mismo patrón que ya usan `LanguageEnum`, `PublishStatusEnum`, etc. — mientras que una clase+config hubiera necesitado un adaptador. (c) **Campo `countries` como tags libres (freeform), con autocompletado cruzando valores usados en otros `services`** — la idea que el Tech Lead mencionó primero — descartada PARA PAÍS específicamente: un país tiene una respuesta objetivamente correcta y finita (no hay razón para que un tenant escriba "Perú", otro "PERU" y otro "peru" como 3 tags distintos), y freeform no da un código ISO limpio para mapear a bandera — perdería exactamente el requisito (b) del pedido ("ISO => NAME"). Esta idea de tags SÍ queda anotada como solución razonable para un campo *distinto* — una clasificación abierta y propia de cada tenant sin catálogo universal — si en el futuro se pide algo así (ej.: "categoría de servicio", "público objetivo"); implementarla requeriría una tabla polimórfica tipo `tags`/`taggables` con `tenant_id`, no un Enum. |
| **Consecuencias** | 1) `App\Enums\CountryEnum` reescrito — 6 casos → 249 (+ `Global`), valores en mayúscula (`ar` → `AR`, etc.), nuevos métodos `flagPath()`, `toApiArray()`, `resolveMany()`. 2) `App\Models\Service::countriesResolved()` nuevo. 3) `ServiceResource`: `countries` ya no `->required()`, `->searchable()` agregado al form y al filtro de tabla. 4) **`Cliente0ServicesSeeder` actualizado** — los 7 servicios ya sembrados usaban códigos en minúscula (`ar`, `uy`, ...) que ya NO existen en el Enum nuevo; el seeder se actualizó a mayúscula (`AR`, `UY`, `GLOBAL`, ...) — **el Tech Lead debe correr `php artisan db:seed --class=Cliente0ServicesSeeder` de nuevo** (usa `updateOrCreate`, es seguro re-ejecutarlo) para que los `services` ya sembrados queden con códigos válidos; si no se re-siembra, esas filas van a quedar con códigos viejos que `CountryEnum::tryFrom()` ya no reconoce (se descartan en silencio en `resolveMany()`, pero el filtro/badge de la tabla de Filament tampoco los va a poder resolver a un label). 5) Sin PHP en este sandbox — balance de llaves/paréntesis/corchetes verificado con un checker Python "PHP-aware" (ignora comentarios y strings) en los 4 archivos tocados, cuadra en los 4. 6) Sistema de tags genérico por tenant queda **explícitamente fuera de alcance** — anotado como alternativa futura, no como tarea pendiente, hasta que haya un pedido concreto de un campo con esa forma. |

## ADR-036 — Árbol de `pages` hasta 3 niveles (`parent_id`), solo organización en Studio

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-31 |
| **Decisión** | Se agrega `parent_id` autorreferenciado (nullable, `FK → pages.id`, `nullOnDelete()`) a la tabla `pages`, permitiendo un árbol de hasta **3 niveles** (página → subpágina → sub-subpágina), a pedido del Tech Lead: "como podemos hacer para armar arbol tree de navegacion hasta en 3 niveles, cuando una pagina tenga parent a otra pagina". Se confirmó explícitamente con el Tech Lead (`AskUserQuestion`) que el árbol es **"Solo organización"** — sirve para agrupar/anidar páginas dentro de Studio (listado con indentación visual `— `), pero **no cambia la URL pública de ninguna página**, que sigue siendo su `slug` plano tal cual hoy (`/mi-slug`, sin prefijos de la jerarquía). El límite de 3 niveles se hace cumplir a nivel de aplicación — el `Select::make('parent_id')` de `PageResource` filtra sus `options()` para excluir: la página misma (al editar), todos sus descendientes (evita ciclos, vía `descendantPageIds()`), y cualquier página que ya esté en profundidad 2 (elegirla como padre crearía un 4to nivel). `Page::depth()` calcula el nivel subiendo por `parent` (máximo 2 saltos + guard defensivo). La tabla de `PageResource` ahora hace eager-load de `parent.parent` y ordena páginas raíz primero, para que la indentación se pueda calcular sin N+1; se quitó `->sortable()` de la columna `title` para no romper ese orden agrupado con un clic de header. |
| **Contexto** | Mismo patrón ya probado en `menu_items.parent_id` (jerarquía de menús, 3 niveles, implementada el mismo día). El Tech Lead reusó la captura de pantalla de esa misma UI de menús como referencia visual al pedir esto para `pages`. La duda de diseño real era si "árbol" implicaba también anidar la URL pública (`/padre/hijo/nieto`) o si era puramente organizacional dentro del panel — se preguntó explícitamente porque tiene implicancias grandes: rutas anidadas exigirían tocar `ResolvesPublicLinks`, la API pública, y la unicidad de `slug` (hoy `[tenant_id, lang_iso, slug]`, plana). El Tech Lead confirmó la opción recomendada de mantenerlo simple: solo organización. |
| **Alternativas consideradas** | (a) **URL anidada según el árbol** (`/padre/hijo`) — la interpretación más "literal" de un árbol de navegación — descartada por decisión explícita del Tech Lead: hubiera requerido rediseñar `ResolvesPublicLinks`, la resolución de rutas del API pública, y cambiar la unicidad de `slug` de plana a compuesta con el path del ancestro, con mucho más riesgo y alcance para un MVP. (b) **Enforce de profundidad máxima con constraint de base de datos** (ej. columna `depth` calculada + `CHECK`) — descartada por simplicidad: un límite fijo y chico (3 niveles) alcanza con validarse en la capa de aplicación (Filament), evita lógica de triggers/constraints en Postgres para un valor que no va a crecer. (c) **Cascade delete de hijos al borrar el padre** — descartada a favor de `nullOnDelete()`: borrar una página no debería poder borrar en cascada otras páginas con contenido propio; los hijos quedan huérfanos (vuelven a nivel raíz) en vez de perderse. |
| **Consecuencias** | 1) Nueva migración `2026_08_31_000006_add_parent_id_to_pages_table.php` — el Tech Lead debe correr `php artisan migrate`. 2) `App\Models\Page`: `parent_id` agregado a `#[Fillable]`, nuevas relaciones `parent()`/`children()` y método `depth(): int`. 3) `PageResource`: nuevo campo `Select::make('parent_id')` en el tab "Configuración" (con `options()` filtrado por ciclos/profundidad), nuevo helper privado `descendantPageIds()`, `table()` con eager-load `parent.parent` + orden raíz-primero, columna `title` con indentación por profundidad y sin `->sortable()`. 4) Sin cambios en `ResolvesPublicLinks`, la API pública, ni la unicidad de `slug` — el contrato público de páginas es idéntico al de antes de esta ADR. 5) Balance de paréntesis/llaves/corchetes verificado (checker Python "PHP-aware") en los 3 archivos tocados — cuadra en los 3. 6) Gap conocido, no resuelto en esta ADR: el `Toggle::make('is_home')` dentro de `HeadingFieldset` (formulario) no impide todavía que dos páginas del mismo tenant queden marcadas como home a la vez — esa protección sí se agregó al toggle de la tabla de `PageResource` (columna `is_home`, ver PROGRESS.md), pero falta replicarla en el form. |

## ADR-037 — Fix de causa raíz: `saveRelationshipsUsing` corrompía campos `MediaUpload` al guardar

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-01 |
| **Decisión** | Se confirma y corrige la causa raíz del reporte crítico del Tech Lead ("si guardo sin cambiar nada, se borra/daña el jsonb"). El `$state` que recibe el closure `saveRelationshipsUsing()` del `Builder` de `blocks` (`PageResource.php`) — usado en vez del `->relationship()` nativo de Filament porque `Block` necesita creación/actualización/borrado manual ligado a `tenant_id`/`sort_order`/tipo — trae los campos `MediaUpload`/`FileUpload` de cada bloque en su **forma interna cruda**: un array de un solo elemento keyeado por el UUID que Livewire genera internamente para identificar el archivo (ej. `{"537a6e80-33e7-4085-8325-5b5a563fcd60": "4"}`), en vez del valor escalar limpio que Filament normalmente entrega (`"4"`). Esa limpieza la hace `Filament\Schemas\Components\StateCasts\FileUploadStateCast::get()` (`Arr::first($state)` en modo single), pero ese cast no se aplica sobre el estado que llega a un `saveRelationshipsUsing` manual — solo se aplica en el camino de deshidratación nativo de Filament (`->relationship()`), que este Builder no usa. El array crudo se guardaba tal cual en el jsonb de `content`/`links`/`properties`; el resolver público (`ResolvesPublicLinks::scalarOrNull()`, ADR de la sesión previa) descarta cualquier id no-escalar, así que la media se resuelve a `null` y desaparece del sitio público — mientras que en Studio el widget la sigue mostrando bien, porque para el propio `FileUpload` esa forma corrupta sigue siendo "un archivo cargado válido" (se reconstruye igual vía `hydrateFiles()`/`Arr::wrap()`). Esto explica por qué el bug pasó desapercibido durante toda la sesión: el contenido sembrado por seeders (`db:seed`) nunca pasa por este código, así que solo se manifestaba la primera vez que alguien guardaba una página real desde Studio — que coincidió con el trabajo reciente sobre el bloque de partners/logos, dando la falsa impresión de que "modificar ese bloque" fue la causa, cuando en realidad cualquier guardado de cualquier página con bloques que tengan `MediaUpload` (split, logos, features, services_grid, heading, hero manual, etc.) dispara el mismo bug — y como se resguardan TODOS los bloques de la página en el mismo guardado, un solo clic de "Guardar cambios" en Home corrompió a la vez la imagen del bloque `split` y los `media_id` de cada item del bloque `logos`. |
| **Diagnóstico** | Confirmado empíricamente, no solo por lectura de código: se agregó un `Log::info()` temporal en el `foreach` de `saveRelationshipsUsing` que registraba el valor real de `content.media_id` justo antes de guardar. El Tech Lead reprodujo el guardado sin cambios en Home y el log real (`storage/logs/laravel.log`) mostró `"media_id_value":{"537a6e80-...":"4"},"media_id_type":"array"` — la prueba directa del bug, no una hipótesis. El log de diagnóstico se retiró una vez confirmada la causa. |
| **Fix** | Nuevo helper `PageResource::unwrapFileUploadState(mixed $value): mixed` (`private static`, recursivo): detecta la firma exacta de esta forma cruda (array de 1 elemento, key con forma de UUID válido vía regex, valor escalar) y la colapsa al valor real; si no matchea esa firma exacta, recorre recursivamente cualquier sub-array sin tocarlo de otra forma. Se aplica a `content`, `properties` y `links` de cada bloque en `saveRelationshipsUsing`, antes de pasarlos a `$block->update()`/`create()`. La detección por regex de UUID (no simplemente "array de 1 elemento") es deliberada — evita falsos positivos sobre objetos legítimos de una sola propiedad (ej. `properties: {"background_color": "#fff"}`, que jamás tiene una key con forma de UUID). La recursión cubre los `MediaUpload` anidados dentro de items de `Repeater` (logos, features, services_grid), no solo los de nivel superior como `split`. |
| **Alternativas consideradas** | (a) **Usar `$component->getChildComponentContainer($key)->getState()` por item**, para forzar la deshidratación cast-aware de Filament en vez de normalizar a mano — descartada por no poder verificarse en este sandbox (sin PHP/Filament ejecutable) y por ser un cambio más invasivo sobre una API interna de Filament 5 (`Builder`/`Schema`) que no está completamente documentada; el fix elegido es autocontenido, no depende de comportamiento interno no verificado, y su corrección se probó con datos reales del log. (b) **Migrar `blocks` a `->relationship()` nativo** de Filament — resolvería esto de raíz de forma más "canónica", pero es un cambio de arquitectura grande (perder el control manual sobre `tenant_id`/`sort_order`/creación-actualización-borrado que motivó `saveRelationshipsUsing` en primer lugar) fuera de alcance de un fix puntual. (c) **Detección genérica sin regex de UUID** (cualquier array de 1 elemento con key string no-numérica) — descartada por riesgo real de falsos positivos sobre `properties`/`content` legítimos de una sola clave. |
| **Consecuencias** | 1) El guard de "estado vacío" agregado horas antes en la misma sesión (ver PROGRESS.md, mismo día) se mantiene como red de seguridad adicional — cubre un caso distinto (el Builder entero sin materializar) y sigue siendo válido. 2) Autoreparación: como el valor ya corrupto en la DB tiene la MISMA forma que este fix sabe normalizar, el próximo guardado de una página con bloques ya corrompidos los deja limpios sin intervención manual — aun así se recomienda correr `db:seed` para partir de datos conocidos-buenos y verificar. 3) No se tocó `ResolvesPublicLinks.php` — sus guards de la sesión previa (`scalarOrNull()`, `uniqueScalarIds()`) ya toleraban este dato corrupto sin tirar 500, solo lo ignoraban; este fix ataca la causa en el punto de guardado, no solo el síntoma en el punto de lectura. 4) **Verificado real por el Tech Lead** (no solo hipótesis): tras corregir también el bug de sliders (ver adenda de abajo), reprodujo el guardado sin cambios en Home y confirmó por log que `content.media_id` llega como escalar (`"4"`/`"5"`) — el fix funciona. |

Causa: `Forms\Components\Slider` (usado por TODAS las propiedades de opacidad/brillo/saturación/contraste de `PropertiesSchema` y del bloque `heading`) tiene su propio state cast (`Filament\Schemas\Components\StateCasts\SliderStateCast::get()`, `floatval($state)`). Como el seeder nunca escribe estas propiedades explícitamente (solo pisa `pretitle`/`title`/`media_id`/`body`), su valor crudo en `$block->properties` es simplemente inexistente — `null` al leerlo — y `floatval(null)` da `0.0`, sin importar que el slider esté configurado con `->default(100)`: ese default de Filament solo se aplica al crear un registro desde cero, no al hidratar datos parciales vía `loadStateFromRelationshipsUsing`. Mismo patrón de fondo que el bug de `MediaUpload` (un state cast que no se aplica en el camino de carga/guardado manual de este Builder), pero en un componente distinto y con consecuencia distinta (imagen invisible por CSS, no imagen ausente). Fix: mapa exhaustivo `PageResource::SLIDER_PROPERTY_DEFAULTS` (cada `Slider::make('properties.X')` de la app con su default real — 100 para brillo/opacidad/saturación/contraste, 0 para escala de grises/sepia/rotación de matiz/desenfoque) + helper `backfillSliderDefaults()` que rellena cualquier key ausente sin pisar valores ya presentes (incluido un `0` puesto a propósito). Aplicado tanto en `loadStateFromRelationshipsUsing` (para que el propio widget en Studio ya muestre el valor correcto) como en `saveRelationshipsUsing` (red de seguridad adicional). Verificado con log real: `properties.media_opacity`/`media_brightness`/`media_filter_saturate`/`contrast`/`brightness` llegaron en `100` (no `0`) en el guardado de confirmación del Tech Lead — mensaje final: "quedó". |

## ADR-039 — Soft delete en `pages` + índice único parcial (`WHERE deleted_at IS NULL`)

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-01 |
| **Decisión** | `pages` gana soft delete (`deleted_at` nullable, trait `Illuminate\Database\Eloquent\SoftDeletes` en `App\Models\Page`), a pedido explícito del Tech Lead: "los slug son únicos por tenant y al ser borrados deberán ser soft-delete, permitiendo diferenciar si es el mismo slug pero uno es soft-delete no cuenta como existente y permitiría generarse con el mismo slug. Solo no deberían duplicarse con contenido activo y no borrado", más "que permita restaurar o recuperar un contenido de la papelera por si borró accidentalmente" y "permita forzar borrado permanente o vaciar basurero... para mantener limpia la tabla manualmente". El unique compuesto original (`tenant_id`, `lang_iso`, `slug`) se reemplaza por un **índice único parcial** — `CREATE UNIQUE INDEX ... | **Contexto** | Disparado por una captura del listado de Páginas mostrando el patrón "slug - Tipo" bajo cada título — el Tech Lead pidió de paso un prefijo "Slug: " explícito para esa línea (para no confundirla con un subtítulo cuando 2 títulos se parecen) y, en el mismo mensaje, formalizó cómo debía comportarse el borrado: hasta ahora `Actions\DeleteAction::make()` hacía un `delete()` duro sin ningún resguardo, sin forma de deshacer un borrado accidental ni de reutilizar un slug ya "usado" por contenido borrado. |
| **Alternativas consideradas** | (a) **Constraint único compuesto que incluya `deleted_at`** (`unique(['tenant_id', 'lang_iso', 'slug', 'deleted_at'])`) — descartada: con `deleted_at` casi siempre `NULL`, Postgres SÍ considera dos `NULL` como distintos en un unique compuesto estándar (a diferencia de un índice parcial), así que en la práctica esto NO habría bloqueado duplicados activos — el comportamiento real que se necesita (unicidad solo entre no-borrados) requiere sí o sí un índice parcial, no un constraint compuesto. (b) **Sin `SoftDeletingScope` explícito, dejar el scope global activo y agregar un toggle propio "Ver papelereados"** — descartada por reinventar lo que `Tables\Filters\TrashedFilter` de Filament ya resuelve de forma estándar y sin código adicional. ## ADR-041 — `background_type` requerido en todo bloque con color de fondo + 3ª opción "Imagen" (excluyente) en `cta`/`heading`

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-02 |
| **Decisión** | `PropertiesSchema::$allFields['background_type']` pasa a ser `->required()` (antes opcional, podía quedar `null`). Se agrega una SEGUNDA variante, `background_type_image` — mismo campo de datos (`properties.background_type`), pero con una 3ª opción `'image' => 'Imagen'` además de `Sólido`/`Degradado` — usada SOLO en los 2 bloques que además tienen su propio campo de imagen de fondo: `cta` (`background_image_id`, ya existía, antes convivía en capas con el color) y `heading` (`content.image_desktop_id`/`_tablet_id`/`_mobile_id`, existían pero el color no tenía ningún tipo de "modo"). En esos 2 bloques, color/degradado e imagen pasan a ser EXCLUYENTES: `background_color` (y por herencia `background_color_secondary`/`gradient_direction`, ya condicionados a `background_type === 'gradient'`) se oculta cuando `background_type === 'image'` (nueva `->visible()` en el propio campo `background_color`, centralizada en `PropertiesSchema.php` — aplica sin importar cuál de las 2 variantes del selector se usó); simétricamente, el/los campo(s) de imagen de `cta`/`heading` se ocultan y solo se vuelven obligatorios cuando el tipo es `image`. El resto de bloques con color de fondo (`hero` en modo Manual, `rich_text`, `image`, `features`, `faq`, `contact_form`, `split`, `testimonials`, `logos`, `services_grid`, Página a nivel general, y los ya existentes `colophon`/`footer_bottom`) ganan el selector `background_type` de 2 opciones (`Sólido`/`Degradado`, ya required) — sin opción "Imagen", porque ninguno de ellos tiene un campo de imagen de fondo alternativo genuino. Excepción explícita: `hero` en modo Manual SÍ tiene una imagen de fondo (`content.background_image_id`), pero esa imagen es la razón de ser del modo Manual (obligatoria siempre, ver ADR-031/032) — no una alternativa opcional al color — así que no se le agrega la 3ª opción ni exclusividad; su `background_color` (que además hoy no tiene ningún consumidor real en `Hero.astro` — solo se usa `slide.properties.slide_background_color`, de Sliders) solo gana el selector de 2 opciones por consistencia de UI, sin cambio de comportamiento. |

Aclarado con `AskUserQuestion` (2 preguntas: alcance del cambio, y qué significa exactamente "ocultar cuando es tipo imagen") — el Tech Lead eligió extender a TODOS los bloques con color de fondo (opción 2) + agregar la 3ª opción "Imagen" donde aplica (opción 3), con comportamiento "ocultar color/degradado cuando el bloque YA tiene una imagen de fondo cargada" (implementado como excluyente por `background_type`, no por presencia de archivo, para que sea determinístico y editable sin ambigüedad). | **Alternativas consideradas** | (a) **Único campo `background_type` con 3 opciones siempre, en todos los bloques** — descartada: bloques sin campo de imagen de fondo (`rich_text`, `features`, `faq`, etc.) mostrarían "Imagen" como opción sin ningún campo de imagen que aparezca al elegirla — callejón sin salida en la UI. Se optó por 2 variantes del mismo Select (`background_type`/`background_type_image`) que escriben al mismo campo de datos, incluida solo la variante correcta por bloque. (b) **Exclusividad basada en "¿hay una imagen ya subida?" en vez de en el valor de `background_type`** — descartada: es lo que el Tech Lead describió coloquialmente, pero requeriría leer el ARCHIVO subido (no solo el tipo) desde `Get`, es frágil (¿qué pasa si subís una imagen y después la borrás — vuelve el color solo automáticamente, sin que el editor lo haya "elegido"?) y menos explícito para el editor de contenido. Se implementó como un tipo explícito y determinístico; el resultado visible es el mismo (con imagen cargada, tipo = Imagen). (c) **Tocar `Heading.astro`/`Cta.astro` a fondo para el nuevo modo** — se hizo SOLO en `Cta.astro` (ya cruza el límite Claude=datos/Antigravity=visual desde ADR previo, documentado ahí mismo) agregando soporte real de degradado vía `resolveBackgroundStyle()` (antes ignoraba `background_type`/gradiente por completo, solo leía `background_color`); `Heading.astro` es un stub explícitamente fuera de este límite (`CLAUDE.md` de cica360: "No reescribir... componentes de bloque — eso es de Antigravity/Gemini") y no se tocó — su color/imagen de fondo sigue sin renderizar en el sitio hasta que Antigravity lo construya, sin regresión (nunca renderizó nada ahí). |
| **Consecuencias** | 1) `PropertiesSchema.php`: `background_type` gana `->required()`; nueva entrada `background_type_image` (3 opciones, mismo campo `properties.background_type`); `background_color` gana `->visible(fn (Get $get) => $get('properties.background_type') !== 'image')`. 2) `PageResource.php`: `background_type`/`background_type_image` sumado a 13 bloques + Página (nivel SEO/Enlaces); `cta` (`Section::make('Fondo')`) y `heading` (`Section::make('Imágenes del Encabezado')` + `Propiedades Visuales`) reescritos con exclusividad real (`->visible()`/`->required()` cruzados en ambos sentidos). 3) `Cliente0ContentSeeder.php`: `background_type => 'solid'` agregado explícito en los 5 bloques que ya sembraban `background_color` (cta home, colophon, footer_bottom, testimonials×2); `colophon`/`footer_bottom` cambian su `background_color` sembrado de `#2D2C4D` a `#191838`. 4) cica360: `Cta.astro` migrado de lectura manual de `background_color` a `resolveBackgroundStyle()` (mismo helper de ADR-040) — gana soporte real de degradado que antes no tenía. `Heading.astro` sin cambios (fuera de alcance, ver arriba). 5) Balance de paréntesis/llaves/corchetes verificado con un tokenizer Python de una sola pasada (el chequeo anterior de 2 pasadas — comentarios primero, strings después — daba falsos positivos con URLs tipo `https://...` dentro de strings, confundiendo el `//` con un comentario; corregido para todo el resto de la sesión) en los 4 archivos PHP y 1 archivo Astro tocados — sin PHP/Node funcional en este sandbox, pendiente `vendor/bin/pint --dirty`, `php artisan test`, `php artisan db:seed` y confirmación visual del Tech Lead en Studio + sitio real (en particular: que el guardado de un bloque `cta`/`heading` existente sin `background_type` seteado no rompa por el nuevo `->required()` — Filament debería resolverlo solo con el `->default('solid')` al abrir el formulario, pero no verificado en vivo). |

"2026 CICA360", `maxLength(120)`); el backend (`ResolvesPublicLinks::transformBlockContent()`, rama `footer_bottom`) arma el copyright público final envolviendo ese fragmento (HTML-escapado con `e()`) en una plantilla FIJA, no editable: `©[fragmento] - Todos los derechos son reservados <br/> Powered by <a href="https://stamless.com" target="_blank">Stamless</a>` — expuesto en la API como `content.copyright_html` (nuevo campo, solo presente para este plan; `content.copyright_text` viaja `null` en este caso, el fragmento crudo no se expone suelto). El plan se asigna y gestiona **a mano** por Stamless/Platform al tenant con el que se pactó el convenio/auspicio B2B — no hay flujo de autoservicio ni conexión al sub-sistema `Plan`/`Subscription` de billing (mismo criterio que `'free'`/`'freemium'`, fuera de alcance del MVP). **CICA360 (Cliente 0) se reasigna de `'free'` a `'sponsorship'`** en `Cliente0Seeder.php` — sigue siendo Headless/free-tier para todo lo demás, gana la posibilidad de poner "2026 CICA360" (o lo que corresponda) en el copyright del footer. |
| **Contexto** | Pedido en vivo del Tech Lead: "Se me ocurre un nuevo plan que tendrá las mismas características del Freemium/Free, pero con el nombre: Auspicio/Convenio, este plan si podrá modificar el copyright pero será con el formato '©[YEAR_AND_COMPANY_NAME_OR_PROJECT_NAME_INPUT] - Todos los derechos son reservados <br/> Powered by Stamless [link]'... este cliente 0 de cica360 será uno de ellos Plan Auspicio/Convención." Aclarado en un mensaje posterior: "Este plan se gestionará y se asignará manualmente por la empresa propietaria B2B al cliente que en convenio o auspicio pactaron" — confirma que no hace falta ningún flujo de upgrade/downgrade automático, ni tocar el sub-sistema de billing. |
| **Alternativas consideradas** | (a) **Reutilizar el gate binario existente (`isFreeTier()`) y simplemente permitir el `TextInput` libre para `'sponsorship'`** — descartada: el pedido es explícito en que el formato NO es libre — el tenant solo aporta el fragmento, la marca "Powered by Stamless" es fija e irremovible en este plan; un `TextInput` libre habilitaría un white-label de facto, contradiciendo el propósito del plan (visibilidad de marca a cambio del convenio/auspicio). (b) **Componer el HTML final en el FRONTEND (cica360) a partir del fragmento crudo + una constante de plantilla ahí** — descartada: dejaría la plantilla (y el dominio `stamless.com` hardcodeado) duplicada en cada consumidor del API en vez de en un solo lugar controlado por Stamless; además el fragmento necesita HTML-escaping antes de insertarse en la plantilla, más natural de garantizar en el backend (mismo principio que `RichContentRenderer` sanitiza `rich_text` antes de salir de la API) que confiando en que cada frontend lo escape bien. Se optó por exponer `copyright_html` YA compuesto y seguro. (c) **Nombre interno `'auspicio'` en vez de `'sponsorship'`** — se prefirió `'sponsorship'` (inglés, consistente con el resto de valores/slugs internos del código, p. ej. `'free'`/`'freemium'`) para el VALOR almacenado; el nombre bilingüe "Auspicio/Convenio" pedido por el Tech Lead queda como el LABEL visible en Studio/documentación, no como el string en DB. |
| **Consecuencias** | 1) `App\Models\Tenant`: `isFreeTier()` incluye `'sponsorship'`; nuevos métodos `isSponsorshipTier(): bool` y `canEditCopyright(): bool` (`! in_array($this->plan, ['free', 'freemium'], true)` — reemplaza la lógica que antes vivía inline como `! isFreeTier()`, porque ya no es equivalente). 2) `PageResource.php`, bloque `footer_bottom`: el campo de copyright pasa de 2 a 3 variantes mutuamente excluyentes por `->visible()` (Placeholder candado / TextInput acotado Auspicio-Convenio / TextInput libre). 3) `ResolvesPublicLinks.php`: rama `footer_bottom` de `transformBlockContent()` compone `content['copyright_html']` para tenants `isSponsorshipTier()`, escapando el fragmento con `e()` y envolviéndolo en la plantilla fija; limpia `copyright_text` en ese caso. 4) `Cliente0Seeder.php`: `plan` de CICA360 pasa de `'free'` a `'sponsorship'`. 5) cica360: `types.ts` — `FooterBottomContent` gana `copyright_html?: string | null`; `FooterBottom.astro` — prioriza `copyright_html` (renderizado como HTML crudo vía `set:html`, con un estilo scoped nuevo para el link "Powered by Stamless") sobre `copyright_text`/fallback. 6) Balance de sintaxis (tokenizer Python) verificado en los 6 archivos tocados (5 PHP + 1 Astro + `types.ts`) — sin PHP/Node funcional en este sandbox, pendiente `php artisan db:seed`, `vendor/bin/pint --dirty`, `php artisan test`, y confirmación visual del Tech Lead: el campo acotado aparece en Studio para CICA360, y el copyright público se ve como "©2026 CICA360 - Todos los derechos son reservados" + "Powered by Stamless" (link real a stamless.com) una vez que se cargue el fragmento (el seeder lo deja vacío a propósito, mismo criterio "sin nada por default" ya establecido para este bloque). |

## ADR-044 — Endpoint público de Servicios (`GET /v1/{tenant}/services`, `/services/{slug}`) + "Servicio" como tipo de enlace de menú

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-02 |
| **Decisión** | Se expone `Service` al API pública, mismo patrón exacto que `Post`: `GET /v1/{tenant}/services` (listado paginado, `ServiceSummaryResource` — uuid/slug/pretitle/title/subtitle/countries/image) y `GET /v1/{tenant}/services/{slug}` (detalle, `ServiceResource` — agrega content/meta/links/properties/published_at, con `content`/`meta`/`properties` normalizados a objeto vía `NormalizesJsonFields`, mismo criterio que `Post`/`Page`). Ambas rutas dentro del mismo grupo de middleware `abilities:content:read` que ya usan posts/pages/menus — sin ability nueva. `ServiceController` filtra por `forLanguage(LanguageEnum::Spanish)` + `published()` + eager-load de `image`, igual que `PostController`. En paralelo, se agrega `MenuItemTypeEnum::Service = 'service'` (entre `Post` y `External`) como cuarto tipo de enlace de menú, resuelto tanto en `MenuController::attachResolvedHrefs()` (API de menús) como en `ResolvesPublicLinks::attachResolvedBlockContent()` (menús embebidos en bloques, ej. `footer_bottom`) — ambos arman el href como `/servicios/{slug}` batcheando los `reference_id` de tipo `service` en una sola query `Service::whereIn(...)->get(['id','slug'])`, mismo criterio anti-N+1 que ya existía para `page`/`post`. |
| **Contexto** | Pendiente explícito documentado en ADR-034: el módulo `Service` (modelo + `ServiceResource` de Filament) existía desde antes pero nunca tuvo endpoint público ni forma de enlazarse desde un menú — quedó anotado como "Estado: no iniciado" en ese ADR. Se retoma ahora porque el rediseño del menu builder (ver ADR-045) necesita un cuarto tipo de enlace real ("tipo pagina interna, post del blog, servicio, o custom link", pedido explícito del Tech Lead) y "servicio" sin URL pública sería un tipo de enlace roto por diseño. Ante 3 alternativas planteadas (agregar el tipo ya sabiendo que el link no resuelve / omitir "Servicio" del menú builder por ahora / construir primero el endpoint público completo), el Tech Lead eligió explícitamente la tercera: "Construir el endpoint de servicios primero". |
| **Alternativas consideradas** | (a) **Agregar `MenuItemTypeEnum::Service` ya mismo, dejando el href sin resolver (`null`) hasta que el endpoint exista** — descartada por decisión explícita del Tech Lead: un tipo de enlace visible en Studio que no lleva a ningún lado es peor experiencia que no ofrecerlo. (b) **Omitir "Servicio" del menu builder en este ciclo, agregarlo en uno futuro** — descartada por la misma decisión: el Tech Lead prefirió cerrar el pendiente de ADR-034 de una vez en vez de posponerlo de nuevo. (c) **Reutilizar `PostResource`/`PostController` genéricos vía un parámetro de "tipo de contenido"** — descartada: `Service` y `Post` son modelos Eloquent y tablas separadas por decisión de esquema ya cerrada (ver esquema del MVP en `ARCHITECTURE.md`), unificarlos detrás de un controller genérico agregaría una capa de indirección no pedida y contradice el criterio "controllers explícitos por recurso" que ya sigue `PageController`/`PostController`/`MenuController`. |
| **Consecuencias** | 1) `App\Http\Resources\Api\V1\ServiceSummaryResource` y `ServiceResource` (nuevos, mismo patrón que sus equivalentes de `Post`). 2) `App\Http\Controllers\Api\V1\ServiceController` (nuevo, `index()`/`show()`, mismo esqueleto que `PostController`). 3) `routes/api.php`: 2 rutas nuevas (`services.index`, `services.show`) dentro del grupo `abilities:content:read` existente, antes de la ruta de menús. 4) `App\Enums\MenuItemTypeEnum`: nuevo `case Service = 'service'` con label "Servicio". 5) `MenuController::attachResolvedHrefs()` y `ResolvesPublicLinks::attachResolvedBlockContent()`: cada uno gana un batch de `Service` (`whereIn('id', $serviceIds)->get(['id','slug'])->keyBy('id')`) y un arm nuevo en el `match` de resolución de href (`'/servicios/'.$service->slug`). 6) `App\Filament\Forms\Components\MenuTreeBuilder::getServiceOptions()` (ver ADR-045) expone `Service::query()->published()->pluck('title', 'id')` para el selector "Servicio de destino" del nuevo builder. 7) cica360: `src/lib/types.ts` gana `ServiceCountry`/`ServiceOffer`/`ServiceCoverage`/`ServiceContent`/`ServiceSummary`/`Service`, y `MenuItemType` se extiende con `'service'`; `src/lib/api.ts` gana `ListServicesParams`/`getServices()`/`getService()`/`getAllServices()`, mismo patrón que la sección de Posts; `src/pages/servicios/[slug].astro` (nuevo, solo el detalle — el listado `/servicios` ya lo sirve una `Page` seedeada de tipo estándar con slug `servicios` vía el catch-all `[slug].astro`, evitando así una colisión de rutas estáticas). 8) Balance de sintaxis (tokenizer Python + `node --check` para el JS del builder) verificado en los archivos tocados — sin PHP/Node funcional en este sandbox, pendiente `vendor/bin/pint --dirty`, `php artisan test`, `npm run build`/`astro check`, y confirmación visual del Tech Lead: que `/v1/{tenant}/services` y `/services/{slug}` respondan, y que `/servicios/{slug}` renderice en cica360. |

## ADR-045 — `MenuTreeBuilder`: campo Filament propio para el árbol de menús (drag-and-drop anidado estilo WordPress), reemplaza los 3 `Repeater`s anidados de `MenuResource`

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-02 |
| **Decisión** | Se reemplaza el form de `MenuResource` (antes 3 `Repeater`s anidados — menú → submenú → sub-submenú, cada nivel una lista aislada sin forma de "arrastrar para anidar" entre niveles) por un campo Filament propio, `App\Filament\Forms\Components\MenuTreeBuilder` (extiende `Filament\Forms\Components\Field`), que edita un array PLANO con profundidad por ítem (`itemsTree`, no una relación Eloquent nativa de Filament) con drag-and-drop real vía SortableJS usado directo (no la directiva `x-sortable` de Filament, que no expone `onStart`/posición del mouse) — arrastrar horizontalmente ~32px anida/desanida un nivel, con botones de indentar/desindentar como alternativa sin mouse. Profundidad máxima configurable (`->maxDepth(3)`, usado con 3: menú → submenú → sub-submenú, igual jerarquía que antes). Cada ítem soporta 4 tipos de enlace (Página interna / Post de blog / Servicio / Custom-External), seleccionables inline por ítem, con el selector de referencia condicional al tipo elegido (`getPageOptions()`/`getPostOptions()`/`getServiceOptions()`, cada uno ya filtrado — páginas excluyen Header/Footer vía `Page::publiclyLinkable()`, servicios solo publicados). La hidratación (árbol real de `MenuItem` → array plano con `depth`) y el guardado (array plano → `parent_id`/`sort_order` reales, con altas/bajas/reordenamiento en una sola pasada transaccional) NO son declarativos: viven en `MenuResource::flattenMenuTree()`/`syncMenuTree()`, conectados al guardado real reemplazando el proceso default de `CreateAction`/`EditAction` vía `->using()` (necesario porque `itemsTree` no es una columna real de `Menu` ni una relación nativa — el guardado default de Filament la ignoraría silenciosamente). |
| **Contexto** | Reporte en vivo del Tech Lead con 3 capturas (la UI de Repeaters anidados actual, un mockup plano estilo WordPress, y el editor clásico de menús real de WordPress con drag+indent): "esta bueno pero no es muy amigable manejar o gestionar los submenus de esa forma, es mejor la segunda captura, desde ahi poder manejar el anidar o cambiar a parent similar a wordpress". Ante la opción de una alternativa más segura (lista plana + `Select` de "padre") vs. drag-and-drop real, el Tech Lead eligió explícitamente la segunda: "Drag-and-drop real estilo WordPress". Se evaluaron 4 plugins de Filament a pedido explícito del Tech Lead (compartió las 4 URLs y pidió comparación + recomendación), con un requisito adicional: "que se pueda personalizar el tipo de enlace como tipo pagina interna, post del blog, servicio, o custom link". Tras la comparación, el Tech Lead decidió explícitamente: "Construir el drag-and-drop propio, sin plugin". |
| **Alternativas consideradas** | (a) **`ysfkaya/filament-menu-builder`** — descartado: pensado para menús de navegación simples de 1-2 niveles con su propio modelo de datos (no compatible con el esquema `menu_items` ya cerrado del MVP), habría requerido adaptar el schema o mantener 2 fuentes de verdad para el árbol. (b) **`solution-forest/filament-tree`** — descartado: es un componente de árbol genérico (para cualquier modelo jerárquico), no un menu builder — no trae edición inline de tipo de enlace/referencia/target por nodo, se habría tenido que construir esa capa igual encima de un plugin de terceros, sin ganar nada sobre construirlo directo. (c) **`notebrainslab/filament-menu-manager`** — descartado: gestiona menú y items en páginas/recursos separados (no inline en el form de `Menu`), UX distinta a la pedida (edición unificada en un solo form, como WordPress). (d) **`biostate/filament-menu-builder`** — descartado: más cercano en espíritu (drag-and-drop anidado) pero con su propio modelo `MenuItem` interno incompatible con el `App\Models\MenuItem` + `menu_items` ya existente del esquema cerrado del MVP; adaptarlo habría significado migrar datos o correr 2 tablas de menú en paralelo. En los 4 casos el bloqueo de fondo es el mismo: el esquema `menus`/`menu_items` del MVP ya está cerrado (no reabrir sin ADR, regla de `CLAUDE.md`) y ningún plugin evaluado se integra con una tabla de items ajena sin asumir su propio modelo — construir un campo Filament propio sobre los modelos ya existentes evita esa fricción por completo, a cambio de mantener el código de drag-and-drop propio. (e) **Lista plana + `Select` de "elemento padre" (alternativa "segura" que se ofreció al Tech Lead junto con drag-and-drop real)** — descartada por decisión explícita del Tech Lead (ver Contexto), quien prefirió la fidelidad a la experiencia de WordPress sobre la menor complejidad de implementación. |
| **Consecuencias** | 1) `App\Filament\Forms\Components\MenuTreeBuilder` (nuevo, extiende `Field`): `maxDepth()`/`getMaxDepth()`, `getPageOptions()`/`getPostOptions()`/`getServiceOptions()`/`getTypeOptions()`/`getTargetOptions()` — vista `resources/views/filament/forms/components/menu-tree-builder.blade.php`. 2) `App\Models\MenuItem`: `booted()` con `creating` — autocompleta `menu_id` desde el `parent_id` cuando el ítem es un submenú (bug separado descubierto y corregido durante este ciclo, ver entrada de PROGRESS.md "3ra vuelta" — `children()` es un self-relation, no hereda `menu_id` automáticamente como sí hace `Menu::items()`). 3) `App\Models\Page`: nuevo scope `scopePubliclyLinkable()` (reutilizado acá para `getPageOptions()`, ya centralizado — ver el fix de "página de destino" del mismo día). 4) `App\Filament\Resources\MenuResource` reescrito: `form()` reemplaza los 3 `Repeater`s por un único `MenuTreeBuilder::make('itemsTree')`; nuevos métodos privados `flattenMenuTree()`/`syncMenuTree()` (algoritmo de pila `$parentAtDepth` por profundidad, mismo principio que usa el editor clásico de WordPress); nuevo método público `createAction()` (factory compartida entre el botón de estado vacío de la tabla y el botón de cabecera de `ManageMenus`, evita duplicar el `->using()` en 2 lugares); `EditAction`/`CreateAction` ambos con `->using()` custom (guardan solo los campos propios de `Menu` — `name`/`slug`/`lang_iso` — y sincronizan el árbol aparte, porque `itemsTree` no es fillable ni relación nativa). 5) `public/js/filament/menu-tree-builder.js` (nuevo, ~290 líneas): componente Alpine (`Alpine.data('menuTreeBuilder', ...)`) registrado en `alpine:init`, usa `window.Sortable` (SortableJS ya vendorizado por `filament/support`) directo con `onStart`/`onEnd` propios para calcular cambio de profundidad por posición X del mouse; incluye auto-reparación de invariante (`normalizeDepths()`, ningún ítem puede quedar más de 1 nivel más profundo que el anterior) y el patrón vaciar+`$nextTick`+reponer (`replaceItems()`) para resolver conflictos de ownership del DOM entre Alpine y SortableJS tras un drag — mismo truco que usa el componente nativo `KeyValue` de Filament. 6) `App\Providers\Filament\PanelCmsProvider`: registra el nuevo JS vía `FilamentAsset::register([Js::make(...)])` + un `<script defer>` manual en el `renderHook(HEAD_END, ...)` con cache-busting por `filemtime()` (mismo patrón ya establecido para `api-console.css`) — necesario para que `Alpine.data(...)` esté registrado antes de que Alpine arranque, sin depender de `php artisan filament:assets` (no ejecutable en este sandbox de desarrollo). 7) Balance de sintaxis (tokenizer Python, con el workaround de `sed` para el falso positivo conocido en atributos PHP 8 `#[Fillable(...)]`) + `node --check` sobre el JS — todos "OK". Sin PHP/Node/navegador funcional en este sandbox, **nada de este campo fue renderizado ni ejercitado en vivo** — queda pendiente la confirmación visual/funcional del Tech Lead en Studio: que el árbol cargue con la jerarquía real, que arrastrar reordene/anide/desanide correctamente, que los 4 tipos de enlace (página/post/servicio/custom) guarden y resuelvan bien, y que crear/editar/borrar en una sola sesión de edición sincronice `menu_items` sin dejar huérfanos. |

## ADR-046 — Endpoint público de Testimonios (`GET /v1/{tenant}/testimonials`), catálogo standalone sin `show` por slug

| Campo | Valor |
|-------|--------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-02 |
| **Decisión** | Se expone `Testimonial` al API pública con un único endpoint, `GET /v1/{tenant}/testimonials` — listado paginado (`TestimonialResource`: uuid/name/role/quote/avatar), filtrado por `is_visible = true`, ordenado por `sort_order` (mismo campo que ya usa el drag-reorder de `TestimonialResource` en Filament). A diferencia de Pages/Posts/Services, **no hay `GET /testimonials/{algo}`**: el modelo `Testimonial` no tiene columna `slug` (ver su migración) y no existe ningún caso de uso real de "pedir un solo testimonio" — siempre se consume como colección completa, igual que ya pasa embebido dentro de `content.items[]` del bloque `testimonials` de una Página. |
| **Contexto** | Al agregar el endpoint público de Servicios (mismo día, ADR-044) apareció como grupo nuevo en el sidebar del API Playground — el Tech Lead notó la ausencia de un grupo equivalente para Testimonios y preguntó por qué. Se le explicó que Testimonios nunca tuvo un endpoint propio (se resuelve embebido dentro de `GET /pages/{slug}`, ver ADR de Testimonials del 2026-08-31) y se ofreció construir uno standalone si lo quería. El Tech Lead confirmó explícitamente: "no hay testimonios" — pidiendo que se agregue, mismo criterio que Services. |
| **Alternativas consideradas** | (a) **`show()` por `uuid`** (ya que no hay `slug`) — descartada: no hay ningún flujo de producto que necesite "linkear a un testimonio individual" (a diferencia de un Post o un Service, que sí tienen página de detalle propia en cica360); agregar un `show()` sin caso de uso real sería superficie de API sin propósito. Si en el futuro surge la necesidad (ej. una página "Casos de éxito" con detalle por testimonio), se agrega entonces con su propio ADR. (b) **Agregar `slug` a la tabla `testimonials` para habilitar un `show()` simétrico a Services/Posts** — descartada por lo mismo: cambiaría el esquema del MVP (ya cerrado, `CLAUDE.md`: "No cambiar stack, multi-tenancy o modelo freemium sin nuevo ADR" — un cambio de schema de este tipo sí necesitaría su propio ADR, y no hay ninguna razón de negocio hoy que lo justifique). (c) **Ordenar por `created_at`, igual que la resolución embebida en bloques (`ResolvesPublicLinks::transformBlockContent()`)** — descartada para el endpoint standalone: ese orden fue pensado para el `content.order` (asc/desc) configurable POR BLOQUE, un concepto que no aplica a un catálogo completo sin filtro; se usa `sort_order` en su lugar, el mismo campo que el admin ya usa para ordenar manualmente en Filament (`TestimonialResource::table()->reorderable('sort_order')->defaultSort('sort_order')`) — más predecible y consistente con Services/Posts, que también ordenan por su campo de orden administrado, no por fecha. |
| **Consecuencias** | 1) `App\Http\Resources\Api\V1\TestimonialResource` (nuevo) — mismo shape `{name, role, quote, avatar}` que ya usa la resolución embebida en bloques, más `uuid`. 2) `App\Http\Controllers\Api\V1\TestimonialController` (nuevo) — solo `index()`, mismo esqueleto que `ServiceController`/`PostController` (paginación, `with('avatar')` anti-N+1). 3) `routes/api.php` — 1 ruta nueva (`testimonials.index`) dentro del grupo `abilities:content:read` ya existente. 4) `App\Filament\Pages\ApiPlayground::PRESETS` — grupo `Testimonials` nuevo (1 preset, sin `.show`). 5) `docs/api/v1.md`/`docs/api/openapi.v1.yaml` — sección/tag/path/schema nuevos, misma pasada que cerró el gap de Services (ver PROGRESS.md). 6) Balance de sintaxis (tokenizer Python) + `openapi.v1.yaml` parseado con `pyyaml` — OK. Sin PHP en este sandbox — pendiente confirmación visual del Tech Lead: el grupo "Testimonials" debería aparecer ahora en el Playground con 1 ejemplo, y `GET /v1/cica360/testimonials` debería devolver los testimonios visibles paginados. cica360 no consume este endpoint todavía (sigue resolviendo testimonios embebidos vía `GET /pages/{slug}`) — queda disponible para un futuro caso de uso (ej. una sección "Casos de éxito" standalone) sin que haga falta tocar el backend de nuevo. |
